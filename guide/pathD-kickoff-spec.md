## 0. 경로 D 한 줄 정의

> **내가 이미 로그인·접근해 있는 목업 화면(배포된 인증 뒤 화면, 또는 로컬 dev 서버)에,
> 내 브라우저에서 SDK를 얹어 어노테이션·캡처·저장하고 단독 실행 HTML로 내보낸다.
> 서버는 목업을 대신 fetch하지 않는다.**

검증 질문: **"로그인을 통과해야만 보이는 화면(SSO 포함)을, 목업을 수정하지 않고
기획서로 만들 수 있는가."**

### 왜 지금 (경로 B 실사용이 만든 실수요)

- 2026-07-11 경로 B 실사용(`hana-color.vercel.app` 및 hanatour 계열 검토) 중, 사용자가
  **"직접 로그인해 둔 상태의 화면을 쓰고 싶다"**는 요구를 명확히 함.
- 경로 B(서버 리버스 프록시)는 원리상 이걸 못 한다: 서버가 **익명으로** 오리진을 fetch하므로
  사용자 세션·쿠키가 없고, 로그인이 외부 IdP로 리다이렉트하면 오리진 밖 리다이렉트 →
  502로 끊긴다 (s2-kickoff §2.1·§4.2, `proxy.ts:155`).
- 이는 스펙이 미리 예고한 지점이다: **PRD 리스크 R5** = "프록시 경로의 인증 우회 표면 →
  안 풀리는 인증은 **경로 D로 우회 안내**". 경로 D는 "B 이후 실수요를 보고 판단"으로
  미뤄져 있었고(s2-kickoff §0 범위 밖), S2가 종료된 지금이 그 "판단 시점"이다.

### 핵심 아키텍처 차이 (경로 B ↔ 경로 D)

| | 경로 B (구현됨) | 경로 D (이 문서) |
|---|---|---|
| SDK 주입 주체 | **서버**가 오리진을 fetch해 응답 HTML에 주입 | **사용자 브라우저**가 이미 보고 있는 페이지에 주입 |
| 인증 상태 | 서버 = 익명 (쿠키 없음) | **사용자가 로그인한 그 세션 그대로** |
| 로그인/SSO | 못 뚫음 (외부 리다이렉트 502) | **문제 자체가 없음** (이미 들어가 있음) |
| SSRF 표면 | 있음 → allowlist·IP 고정 필수 | **없음** (서버가 아무것도 fetch 안 함) |
| 새 보안 표면 | — | **저장 엔드포인트가 임의 오리진에 노출** → 토큰 인증 필요 (§4) |
| 스냅샷 출처 | 클라이언트 캡처(프록시 same-origin 경유) | 클라이언트 캡처(사용자 실제 페이지에서 직접) |

## 1. 경로 D 범위 (확정)

**포함:**

| 포함 | 근거 |
|------|------|
| 브라우저 확장(MV3) 온보딩 — content script SDK 주입 (§2 확정) | FR-ONB-06, 아키텍처 §4 경로 D |
| 프로젝트 토큰 발급·검증 + 저장 엔드포인트 인증 (§4) | 저장이 임의 오리진에 노출되는 새 표면 |
| 확장 background 경유 저장 (§4.2 — CORS 불필요) | 주입된 SDK가 서비스 도메인 밖에서 저장 |
| 콘솔 온보딩 3번째 선택지 + 설치/토큰 안내 (§3) | detailed-spec §2.3 확장 |
| E2E: **로그인 뒤 화면** 시나리오 (§7) | 경로 D의 존재 이유를 그대로 검증 |

**범위 밖(경로 B와 동일 기조 유지):** 옵션 S 스니펫/북마클릿(§2 — 후속 실수요 판단),
저장 CORS(§4.2 — S 도입 시에만), 마스킹은 S2 것을 **그대로 재사용**(신규 없음),
편집기·앵커·캡처·뷰어·export는 **무변경**, 장면 전이·흐름도·LLM·레포 빌드(경로 C)·실시간
협업은 여전히 제외. 확장 스토어 공개 배포는 실사용 판정 후 판단(§8-3).

**핵심 재사용(좋은 소식):** 설계 원칙 #3("편집은 라이브, 캡처는 클라이언트 브라우저에서만")
덕분에 캡처·저장·뷰어·export가 이미 클라이언트에서 돈다. 경로 D는 **온보딩 계층 + 저장 인증**만
새로 필요하고, 나머지는 S1·S2 자산을 그대로 쓴다.

## 2. 결정: 주입 메커니즘 — **브라우저 확장 (옵션 E, 2026-07-11 사용자 확정)**

경로 D의 성패는 "무엇으로 SDK를 주입하나"에 달렸다. 아키텍처 가이드 §4는 "스니펫/북마클릿"으로
느슨하게 적었지만, 경로 D의 존재 이유(로그인 뒤 CSP 엄격한 실화면)를 커버하는 것은 확장뿐이다.
**옵션 S(스니펫)는 이번 범위에서 제외한다** — 로컬 dev 서버용 실수요가 확인되면 후속 판단
(확장이 로컬 페이지에도 주입되므로 S 없이도 로컬 케이스 대부분이 커버된다).
아래 두 옵션 비교는 결정 근거로 보존한다.

### 옵션 S — 스니펫 / 북마클릿

목업 페이지에 `<script src="{서비스}/sdk.js" data-project data-token>` 한 줄(또는 북마클릿)을 주입.

- **장점**: 설치 0, 기존 `sdk.js` 서빙을 그대로 재사용, 로컬 dev 서버·CSP 느슨한 사이트에서 즉시 동작.
- **한계(사용자 케이스와 충돌)**:
  - 대상 페이지의 **CSP `script-src`**가 서비스 도메인을 막으면 sdk.js 로드 자체가 차단됨.
    로그인 뒤 실서비스는 대개 CSP가 엄격 → **이 케이스가 정확히 막힌다.**
  - SDK가 서비스로 보내는 저장 요청이 **CORS**에 걸림(서버가 CORS 허용해도 CSP `connect-src`가
    또 막을 수 있음).
  - 페이지 이동마다 재주입 필요(라우트 전환 SPA는 그나마 유지, MPA는 매 페이지 재실행).

### 옵션 E — 브라우저 확장 (Manifest V3 content script) — **초안 권장**

확장의 content script가 SDK를 주입. 사용자가 지적한 "확장에서는 그런 게 가능"이 이것.

- **장점**:
  - content script는 페이지 CSP의 **script-src 제약을 우회**해 주입 가능(확장 자원 로드).
  - 저장은 background service worker가 `host_permissions`로 **CORS 없이** 서비스에 전송
    (content script → message → background → fetch). 페이지 CSP `connect-src`도 우회.
  - 페이지 이동에도 매칭 규칙으로 **지속 주입**, 툴바 팝업으로 on/off·프로젝트 바인딩.
- **비용**:
  - MV3 확장 **패키징·배포**가 필요(개발 중 unpacked 로드 / 사내 배포는 정책 푸시 / 공개는 웹스토어).
  - 코드량·리뷰 증가, 브라우저별(Chrome·Edge 한정 — 어차피 편집 환경 지원 범위 ID-02와 일치).
  - 기존 `sdk.js`(IIFE 단일 번들)를 content script 컨텍스트에 싣는 로더 래핑 필요.

### 확정 근거

경로 D의 존재 이유가 "로그인 뒤 CSP 엄격한 실화면"인데 그건 E라야 뚫린다. S만으로는
실수요(직접 로그인해 둔 화면 사용)를 못 채운다. 단계안(S 먼저 → E)도 검토했으나, S가
목표 케이스를 못 뚫는 이상 중간 단계의 검증 가치가 낮아 기각. — 2026-07-11 사용자 확정.

## 4. 결정(제안): 보안 — SSRF는 사라지고, 저장 인증이 새로 생긴다

경로 D는 **서버가 목업을 fetch하지 않으므로 SSRF 표면이 없다**(경로 B의 §4.1 allowlist·IP 고정
전체가 경로 D엔 불필요). 대신 **새 표면**이 열린다: SDK가 이제 서비스 도메인 밖 임의 오리진에서
돌며 저장 API를 호출한다. 여기가 방어 지점.

### 4.1 프로젝트 토큰 (신규)

- 경로 D 프로젝트 생성 시 **불투명 토큰** 발급(`tok_` + 충분한 엔트로피). 프로젝트당 1개, 재발급·폐기 가능.
- 저장 계열 요청(`PUT /projects/:id`, `POST /projects/:id/assets`, `POST .../export`)은
  경로 D 프로젝트에 한해 **`Authorization: Bearer {token}` 필수**. 토큰 불일치·부재 → 401.
- 토큰은 서버에 해시로 저장(평문 미보관). SDK/확장은 바인딩 시 1회 받아 로컬 보관.
- 근거: same-origin 서브도메인 신뢰(경로 A·B)가 경로 D엔 없다 — 임의 페이지가 남의 프로젝트에
  쓰지 못하게 토큰이 유일한 경계.

### 4.2 CORS — 구현하지 않는다 (옵션 E 확정의 귀결)

- 저장 요청은 확장의 **background service worker**가 `host_permissions`로 보내므로 CORS
  대상이 아니다 (content script → message → background → fetch). 서버는 **토큰 검증만**
  하면 되고, 저장 엔드포인트에 CORS 허용을 추가하지 않는다 — 표면을 넓히지 않는 쪽이 단순.
- 후속에 옵션 S(스니펫)를 도입하게 되면 그때 토큰 게이트 CORS를 추가한다 (이 문서 §9에 기록 후).
- 조회·서빙 계열은 기존 정책 유지.

### 4.3 마스킹·데이터 범위 (S2 재사용)

- 경로 D 스냅샷도 실데이터를 담을 수 있다 → **S2 마스킹을 그대로 적용**(신규 없음).
- SDK가 서버로 보내는 범위는 S1·S2 그대로(spec + 명시적 캡처 스냅샷뿐, NFR-04).

### 4.4 캡처 시 cross-origin 리소스 (경로 B보다 빈번)

- 실서비스는 CDN·외부 폰트를 더 많이 쓴다 → 캡처(single-file) 인라인이 CORS로 실패할 여지가
  경로 B보다 크다. s2-kickoff §2.3 원칙 유지: 실패 리소스는 스냅샷에서 제거(네트워크 0건 우선),
  캡처 배지에 실패 수 표기. background fetch 인라인 완화는 범위 밖으로 확정(§8-4) —
  실사용에서 문제가 실측되면 그때 판단.

| T23 | 확장 팝업(프로젝트 바인딩) + background 저장 (§4.2) | 팝업서 프로젝트 ID·토큰 바인딩 → 임의 사이트에서 편집·캡처·저장이 background 경유로 성공 |
| T24 | E2E: 로그인 뒤 화면 시나리오 (§0 검증질문) | 아래 DoD |
| T25 | docs/ 최종 동기화 + 실사용 판정 기록 | 구현 결과 반영, 판정 기록 |

### 경로 D Definition of Done

로그인 fixture(로그인 폼 + 인증돼야 보이는 보호 화면을 가진 앱)를 대상으로:

1. 사용자가 **직접 로그인**(서버가 대신 하지 않음) → 보호 화면 진입
2. 확장(content script)이 SDK 주입 → FAB·패널 표시
3. 보호 서브 화면에서 장면 등록·어노테이션·설명 입력(로그인 세션 위에서 편집 동작)
4. 캡처 → **토큰 인증**으로 spec·스냅샷 저장(서버는 목업을 fetch하지 않음)
5. (실데이터면) 마스킹 규칙 적용
6. export → 새 컨텍스트 file:// 오픈 → 마커 위치(≤2px)·설명 일치·**네트워크 0건**·마스킹 원문 0회
7. 보안 회귀: 토큰 없는 저장 요청 401, 남 프로젝트 토큰으로 쓰기 거부

통과 + **실사용 1회**(실제 로그인 뒤 화면으로 기획서 1부 완성) 판정을 §9에 기록하면 경로 D 종료.

> E2E 참고: Playwright에서 MV3 확장은 `launchPersistentContext` + `--load-extension`으로
> 로드한다 (구식 headless 미지원 — 신 headless로 동작). 세부는 T24 구현 시 확정.

## 8. 확정된 결정 (초안의 "결정 대기" 5건 — 2026-07-11 해소)

1. **주입 메커니즘 = 옵션 E(확장)** — 사용자 확정. 옵션 S(스니펫)는 범위 밖, 후속 실수요 판단 (§2).
2. **토큰 저장**: spec.json 밖, 서버 데이터 디렉토리의 프로젝트별 메타 파일에 **해시만** 저장.
   근거: spec.json은 클라이언트 PUT이 전체 교체 — tokenHash를 담으면 덮어쓰기·유출 표면.
   만료 없음(사내 도구 규모에 회전 정책은 과잉), 콘솔에서 수동 재발급·폐기(재발급 시 구 토큰 즉시 무효).
3. **배포**: 개발·실사용 판정까지 **unpacked 로드**(Chrome/Edge 개발자 모드 — 지원 브라우저
   ID-02와 일치). 사내 정책 배포·스토어 공개는 실사용 판정 후 별도 결정.
4. **캡처 cross-origin 완화**: 범위 밖. 기본 동작(실패 리소스 제거 + 배지 표기, s2 §2.3) 유지.
   실사용에서 시각 완전성 문제가 실제로 확인되면 background fetch 인라인을 그때 판단.
5. **로드맵 위치**: 독립 스프린트 **S2.5**로 승격 (S3 앞). PRD §7.1 로드맵의 "후속 판단" 행에서
   경로 D를 꺼내 확정 행으로 — docs/ 동기화에 포함.
