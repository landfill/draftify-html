## 1. 배경: 왜 방향 전환인가

기존 Draftify 파이프라인(크롤링 → LLM 분석 → PPT 생성)에서 확인된 실질적 한계:

| # | 한계 | 근본 원인 |
|---|------|----------|
| 1 | 프로세스 흐름도가 제대로 생성되지 않음 | 흐름(전이) 정보는 DOM 캡처에 존재하지 않음. LLM이 **추측**으로 채움 |
| 2 | SPA 버튼 클릭/화면 전환을 헤드리스로 구분 어려움 | 헤드리스 크롤러는 "사람이 의미를 부여한 상태 전이"를 알 수 없음 |
| 3 | 디스크립션이 부정확한 정보로 채워짐 | 스크린샷 → LLM 역추론은 원래 기획 의도를 복원할 수 없음 |
| 4 | 작은 서비스에도 10분+ 소요 | 크롤링 + 다단계 LLM 호출의 순차 파이프라인 |
| 5 | AI API 과다 사용, 저가 모델 전환 시 품질 저하 | 전체 산출물을 LLM 생성에 의존하는 구조 |

**공통 근본 원인**: 기획 의도(왜 이 버튼이 있고, 눌렀을 때 무슨 일이 일어나야 하는가)는
목업의 밖(사람 머릿속)에 있는데, 이를 **역공학으로 추론**하려 했기 때문.

**새 방향의 핵심 전환**: 추론을 포기하고, 의도를 아는 사람이 목업 위에 **직접 주석을 다는**
구조로 바꾼다. 목업 자체가 기획서가 된다 (Living Spec / Mockup-as-Spec).

- LLM은 "생성 주체"에서 "초안 보조"로 강등 → 비용/품질 문제 구조적 해소
- 화면 전이는 사람이 명시 → 흐름도 정확성 문제 해소
- 크롤링 불필요 → 10분 소요 문제 해소

## 2. 목표 사용자 경험 (제안하신 안 정리)

```
┌────────────────────────────────────────────┬──────────────────────┐
│                                            │  디스크립션 패널      │
│   목업 화면 (원본 그대로 동작)               │                      │
│                                            │  ① 검색어 입력        │
│   [검색창 ①]  [로그인 ②]                    │     - 2자 이상 입력 시 │
│                                            │       자동완성 노출    │
│   ┌──────────────┐                         │  ② 로그인 버튼        │
│   │  상품 목록    │                         │     - 미로그인 시     │
│   │  [담기 ③]    │                         │       /login 이동     │
│   └──────────────┘                         │  ③ 장바구니 담기      │
│                                            │     - POL-012 참조    │
└────────────────────────────────────────────┴──────────────────────┘
```

1. PC 브라우저에서 목업이 좌측, 디스크립션 패널이 우측에 배치
2. 목업의 인터랙션 요소(버튼, 메뉴, 입력창 등)에 **숫자 어노테이션** 부착
3. 우측 패널에서 각 번호에 대한 설명을 **직접 입력**
4. 편집 내용은 로컬(localStorage)에 저장
5. **HTML 내보내기**로 단독 실행 가능한 기획서 산출물 생성

이 그림은 그대로 유효하다. 아래는 이를 실현하기 위한 설계 결정들이다.

## 3. 아키텍처 결정 1: 오버레이를 목업에 어떻게 붙일 것인가

세 가지 방식이 있고, **목업 원본 레포가 있다는 전제라면 B안을 권장**한다.

### A안. iframe 셸(Shell) 방식 — 목업 무수정

기획서 앱(셸)이 별도로 뜨고, 목업을 iframe으로 로드한 뒤 postMessage로 통신.

```
[기획서 셸 앱] ──iframe──▶ [목업 사이트]
      │                        │
      └──── postMessage 브릿지 ─┘
```

- 장점: 목업 레포를 전혀 건드리지 않음. 여러 목업에 재사용 가능
- 단점: cross-origin이면 iframe 내부 DOM 접근 불가 → **동일 오리진 프록시**가 필수
  (셸 dev 서버가 `/mockup/*`을 목업으로 리버스 프록시). SPA 라우팅·팝업·스크롤 동기화 등
  브릿지 유지비가 생각보다 큼

### B안. 오버레이 SDK 주입 방식 — 권장 ★

목업 레포에 스크립트 한 줄(또는 Vite/Next 플러그인)로 오버레이 SDK를 주입.
개발 모드 또는 `?spec=1` 쿼리에서만 활성화.

```html
<!-- 목업 index.html, dev 전용 -->
<script src="https://localhost:PORT/spec-overlay.js" defer></script>
```

SDK가 하는 일:
- `document.documentElement`에 우측 패널 레이아웃 주입 (목업 영역을 `width: calc(100% - 380px)`로 축소하거나, 목업을 건드리지 않고 패널을 `position: fixed` 우측 도킹)
- 어노테이션 마커 렌더링 (Shadow DOM 사용 → 목업 CSS와 완전 격리)
- 편집 모드 토글: 편집 모드에서는 클릭이 어노테이션 부착으로 동작, 미리보기 모드에서는 목업이 원래대로 동작

- 장점: 같은 오리진이므로 DOM/라우터/상태에 완전 접근. 구현 난이도 최저. SPA 전환 감지 용이
- 단점: 목업 레포에 (미미한) 수정 필요 — 전제상 원본 레포가 있으므로 문제 아님

### C안. 브라우저 확장 / 북마클릿 — 보조 수단

원본 레포 접근이 불가한 목업(외부 데모 등)용 fallback. B안의 SDK를 북마클릿으로 감싸면 거의 공짜로 얻어진다.

**결정 가이드**: B안을 기본으로 구현하되, SDK 코어를 주입 방식과 무관하게 작성하면
C안(북마클릿)은 부산물로 확보되고, A안이 필요해지면 브릿지만 추가하면 된다.

## 4. 아키텍처 결정 2: 어노테이션을 무엇에 앵커링할 것인가

가장 흔한 실패 지점. 좌표(x, y)에 붙이면 반응형/스크롤/리렌더에서 전부 깨진다.
**3단계 앵커 전략**을 권장:

| 우선순위 | 방식 | 설명 |
|---------|------|------|
| 1순위 | `data-spec-id` 명시 부여 | 편집 모드에서 요소 클릭 시 SDK가 자동으로 고유 id를 요소에 부여하고, (가능하면) 소스에도 반영하도록 유도. 가장 견고 |
| 2순위 | 구조적 셀렉터 자동 생성 | `#root > nav > button:nth-of-type(2)` + 텍스트 내용 + 접근성 속성(aria-label, role)을 조합한 다중 시그니처. 하나가 깨져도 나머지로 재탐색 |
| 3순위 | 스크린샷 영역(rect) fallback | 요소를 못 찾으면 마지막으로 알던 위치에 "위치 불확실" 표시로 렌더 — 조용히 사라지게 두지 않는 것이 중요 |

앵커 재해석(resolve)은 렌더 시마다 수행하고, 2순위로 찾았을 때는 시그니처를 자동 갱신한다.

## 5. 아키텍처 결정 3: "장면(Scene)" 개념 — SPA 상태 문제의 해법

기존 크롤러가 실패한 지점이 바로 이것: SPA에서 "화면"이란 URL이 아니라
**URL + 사용자가 의미를 부여한 상태**(모달 열림, 탭 선택, 검색 결과 표시 등)다.

자동 감지에 다시 의존하지 말고, **사람이 장면을 선언**하게 한다:

1. 작성자가 목업을 원하는 상태로 조작 (메뉴 열고, 모달 띄우고)
2. 패널의 **"이 화면을 장면으로 추가"** 버튼 클릭
3. SDK가 그 순간을 장면으로 등록: `{ id, 이름, URL/route, DOM 스냅샷, 스크린샷 }`
4. 어노테이션은 항상 **특정 장면에 소속**됨

라우트 변경(history API 후킹)은 "새 장면을 만드시겠습니까?" 제안 트리거로만 사용
— 자동 생성이 아니라 **제안**. 이것이 기존 크롤러의 실패에서 얻은 교훈을 반영하는 지점이다.

### 장면 전이 = 프로세스 흐름도의 원천 데이터

어노테이션 스키마에 `transition` 필드를 두어 "이 버튼을 누르면 → 장면 X로 이동"을
작성자가 지정하게 하면, **scenes + transitions는 곧 방향 그래프**다.

```
프로세스 흐름도 = 이 그래프의 자동 렌더링 (Mermaid 등)
```

기존 파이프라인에서 가장 부정확했던 프로세스 흐름도가, 사람이 입력한 정확한
전이 데이터 기반의 **결정론적 산출물**로 바뀐다. LLM 불필요.

## 6. 데이터 모델

```jsonc
// spec.json — 산출물의 단일 진실 원천
{
  "version": 1,
  "project": { "name": "...", "mockupOrigin": "http://localhost:3000" },
  "scenes": [
    {
      "id": "scene-login",
      "title": "로그인",
      "route": "/login",
      "stateNote": "이메일 탭 선택 상태",
      "snapshotHtml": "snapshots/scene-login.html",   // 내보내기 시 생성
      "screenshot": "screenshots/scene-login.png"     // fallback
    }
  ],
  "annotations": [
    {
      "id": "anno-3",
      "sceneId": "scene-login",
      "number": 3,
      "anchor": {
        "specId": "login-submit-btn",                 // 1순위
        "selector": "form > button[type=submit]",     // 2순위
        "text": "로그인",
        "rect": { "x": 0.42, "y": 0.61, "w": 0.16, "h": 0.05 }  // 3순위 (비율 좌표)
      },
      "title": "로그인 버튼",
      "description": "이메일/비밀번호 유효성 통과 시 활성화. 실패 3회 시 캡차 노출 (POL-014).",
      "policyRefs": ["POL-014"],                      // 기존 ID 체계와 연계 가능
      "transition": { "toSceneId": "scene-home", "condition": "성공 시" }
    }
  ]
}
```

### 저장 전략: localStorage는 "임시", 파일이 "정본"

제안하신 대로 편집 중엔 localStorage에 자동 저장(디바운스)하되, 이를 정본으로 삼으면 안 된다
(브라우저/기기 종속, 팀 공유 불가, 유실 위험). 계층을 나눈다:

| 계층 | 매체 | 역할 |
|------|------|------|
| L1 | localStorage | 편집 중 자동 저장 (크래시 복구) |
| L2 | `spec.json` 내보내기/불러오기 | 정본. **목업 레포에 커밋** → 기획서가 코드와 함께 버전 관리됨 |
| L3 | HTML 내보내기 | 배포용 최종 산출물 (읽기 전용) |

spec.json이 목업 레포에 커밋되면 "목업 수정 → 기획서도 같은 PR에서 갱신"이라는
이상적인 워크플로우가 생긴다.

## 7. 핵심 질문: 백엔드 연동 목업은 어떻게 하나

감을 못 잡으신 지점. 결론부터:

> **문제를 "편집 시점"과 "산출물 시점"으로 쪼개면 대부분 해소된다.**
> 편집 시점엔 백엔드가 있어도 되고, 산출물 시점엔 백엔드가 필요 없게 만들면 된다.

### 7.1 편집 시점 — 백엔드 그대로 사용 (문제 없음)

어노테이션은 **렌더된 DOM**에 붙지, API에 붙지 않는다. 작성자가 실제 백엔드가 돌아가는
개발 환경에서 목업을 조작하며 어노테이션을 달면 된다. 로그인이 필요하면 작성자가
로그인하면 된다. 이 시점엔 백엔드 의존이 전혀 문제가 아니다.

### 7.2 산출물 시점 — "장면 캡처(Scene Freeze)"이 정답

단독 실행 HTML 산출물에서 백엔드가 문제가 되는 이유는 "산출물이 목업을 다시 실행해야
한다"고 가정하기 때문이다. 이 가정을 버린다:

> 기획서의 본질은 **특정 상태의 화면 + 설명**이지, 동작하는 앱이 아니다.
> 인터랙션(화면 전환)은 실제 실행이 아니라 **장면 간 하이퍼링크**로 표현하면 충분하다.

**장면 캡처 방식**: "장면으로 추가" 시점에 렌더 완료된 DOM을 통째로 직렬화한다
(SingleFile과 동일한 원리 — CSS 인라인화, 이미지 → data URI, 스크립트 제거).
API 응답은 이미 DOM에 반영된 상태이므로, **캡처된 장면은 백엔드가 필요 없다.**

내보낸 HTML의 동작:

```
[산출물 HTML (단일 파일, 어디서나 열림)]
 ├─ 장면 목록 사이드바
 ├─ 장면 뷰어: 캡처된 DOM 렌더 (읽기 전용, 스크립트 없음)
 ├─ 어노테이션 마커 + 디스크립션 패널
 └─ transition 링크: "① 클릭 시 → [주문완료 장면 보기]" ← 실행 대신 이동
```

이 방식의 파급 효과:
- 백엔드 문제 소멸 (인증, DB, 외부 API 전부 무관)
- `file://`로 열어도 동작 (메일 첨부, 위키 업로드 가능)
- 목업이 나중에 죽거나 바뀌어도 산출물은 그 시점 상태를 보존 (기획서의 아카이브 속성에 부합)

### 7.3 대안 비교 — 인터랙티브 재현이 정말 필요하다면

| 전략 | 원리 | 평가 |
|------|------|------|
| **장면 캡처** ★ | 렌더된 DOM 직렬화, 전이는 링크 | 구현 쉬움, 백엔드 무관, 기획서 목적에 부합. **기본 채택** |
| API 녹화/재생 | 편집 중 fetch/XHR을 인터셉트해 기록, 산출물에 인라인 재생기 포함해 SPA 번들과 함께 내보냄 | 진짜 인터랙티브. 단, SPA 빌드 포함 필요, 녹화 안 된 경로에서 깨짐, 민감 데이터가 산출물에 포함될 위험. 비용 대비 효용 낮음 |
| MSW(Mock Service Worker) fixture | 목업 레포에 MSW를 붙여 백엔드 없이 도는 데모 모드 구축 | 근본적이지만 목업 레포별 구축 비용 큼. 또한 Service Worker는 `file://`에서 동작 불가 → 단독 HTML 산출물엔 부적합 |
| 스크린샷 전용 | 장면을 이미지로만 저장 | 최후의 fallback. DOM 직렬화 실패 시(canvas/WebGL 위주 화면) 자동 대체 |

주의: API 녹화/재생이나 MSW를 선택하더라도 **녹화된 응답에 실데이터(개인정보 등)가
포함될 수 있다.** 산출물이 사외로 나갈 수 있다면 장면 캡처 + 내보내기 전 마스킹 단계를
두는 편이 안전하다. 장면 캡처도 화면에 보이는 실데이터는 포함하므로, 내보내기 직전
"텍스트 치환(마스킹) 편집" 기능을 M2 이후 고려할 것.

### 7.4 요약 판단 기준

```
목업이 백엔드 필요? ──아니오──▶ 그냥 진행 (모든 방식 가능)
        │예
        ▼
산출물에서 실제 조작이 필수인가? ──아니오(대부분)──▶ 장면 캡처 ★
        │예 (드묾: 임원 시연용 등)
        ▼
목업 레포에 투자 가능? ──예──▶ MSW 데모 모드 (산출물은 정적 호스팅 필요)
        │아니오
        ▼
API 녹화/재생 (범위 한정, 데이터 마스킹 필수)
```

## 8. 기존 Draftify 자산과의 관계 — 코드 재활용 없음

> 2026-07-06 개정: 초판에는 크롤러 시딩·LLM 초안·PPT 변환 등 코드 재활용 표가 있었으나 철회한다.
> 기존 파이프라인의 비효율(다단계 LLM 생성, 헤드리스 크롤링)은 코드가 아니라 실행 방식의
> 문제였고, 그 실행 방식 자체가 폐기 대상이므로 가져올 코드가 없다.

**계승하는 것은 코드가 아니라 두 가지다:**

| 계승 대상 | 내용 |
|-----------|------|
| 산출물 규범 | `docs/design/auto-draft-guideline.md`의 섹션 구조/ID 체계(POL-*, SCR-*). `policyRefs` 필드가 연결 고리 |
| 실패의 교훈 | 자동 추론 금지(의도는 사람이 입력), 서버 헤드리스 재현 금지(로그인 후 화면 재현 불가), SPA 상태 자동 감지 의존 금지 |

**명시적으로 계승하지 않는 것과 이유:**

- `scripts/crawler.js` (장면 시딩 포함): 목업마다 환경이 제각각이라는 것이 크롤러 실패의
  원인 그 자체이며, "캡처는 사용자 브라우저에서"라는 본 문서의 핵심 결정과 모순된다.
  새 모델에서 장면 등록은 버튼 한 번이라 시딩으로 아낄 노동도 없다
- LLM 클라이언트: 필요해지는 시점(§9 M3)에도 호출 패턴이 전혀 다르므로(장면 하나+요소
  하나 → 한두 문장 초안, 사람이 확정) 수십 줄 신규 구현이 맞다
- `scripts/generate_ppt.py`: **PPT는 산출물 범위가 아니다.** 탈 PPT가 이 프로젝트의 출발
  동기이며, 산출물은 단독 HTML 단일 형식이다

## 9. 단계별 로드맵

### M1 — 검증 (핵심 가설: "이 편집 UX가 실제로 편한가")
- 오버레이 SDK: 주입 스크립트 1개 (Shadow DOM 패널 + 마커)
- 요소 클릭 → 번호 부착 → 우측 패널에서 설명 입력
- localStorage 자동 저장, spec.json 내보내기/불러오기
- 장면 캡처(DOM 직렬화) + 단독 HTML 내보내기 (장면 1개짜리라도)
- 실제 목업 하나에 붙여서 기획서 1부를 끝까지 만들어볼 것 — 여기서 UX 판정

### M2 — 기획서로서의 완성도
- 다중 장면 + 장면 간 transition 지정 UI
- transition 그래프 → 프로세스 흐름도 자동 렌더 (Mermaid)
- 앵커 3단계 fallback (재탐색, rect fallback)
- POL-* 정책 참조 필드, 산출물 HTML에 정책정의서 섹션 통합
- 내보내기 전 텍스트 마스킹 편집

### M3 — 보조 자동화 (선택)
- LLM 디스크립션 초안 제안 (신규 소형 구현 — 장면 하나+요소 하나 → 한두 문장, 사람이 확정)
- 북마클릿 배포판 (레포 접근 불가 목업용)

### 범위에서 뺄 것 (명시적 non-goal)
- **PPT 등 HTML 외 산출물 형식** (탈 PPT가 이 프로젝트의 출발 동기 — 산출물은 단독 HTML 하나)
- 크롤러 기반 장면 자동 시딩 (§8 — 헤드리스 재현 금지 원칙과 모순)
- 실시간 협업 편집 (spec.json + git으로 충분히 시작 가능)
- 산출물에서의 실제 앱 실행 (7절 결론대로 장면 캡처로 대체)
- 모바일 편집 환경 (뷰포트별 장면 캡처로 모바일 "표현"은 가능하되, 편집은 PC 전제)

## 10. 리스크와 열린 질문

1. **DOM 직렬화의 까다로운 케이스**: iframe 중첩, canvas/WebGL, CSS-in-JS 런타임 스타일,
   웹폰트 라이선스. → 스크린샷 fallback을 처음부터 내장할 것
2. **목업 리렌더 시 마커 위치 갱신**: React 리렌더로 요소가 교체되면 마커를 다시 붙여야 함
   → MutationObserver + 앵커 재해석 (4절), 성능 위해 디바운스
3. **spec.json 충돌**: 여러 명이 동시에 편집하면 git 충돌 → M1~M2에서는 "화면 담당자 1인"
   운영 규칙으로 회피, 필요 시 M3+에서 서버 도입
4. **어노테이션 번호 체계**: 장면별 재시작(①②③...) vs 전역 유일 → 장면별 재시작 + 내부 id는
   전역 유일(anno-*)을 권장 (읽는 사람 기준 + 참조 무결성 동시 확보)

## 11. 결론

- 제안하신 방향(목업 = 기획서, 숫자 어노테이션 + 우측 디스크립션 + HTML 내보내기)은
  기존 파이프라인의 5가지 한계를 **구조적으로** 해소하는 올바른 전환이다.
- 구현은 **오버레이 SDK 주입(B안) + 사람이 선언하는 장면(Scene) + 3단계 앵커**로.
- 백엔드 문제는 **"편집은 라이브, 산출물은 장면 캡처"**로 분리하면 사라진다.
  산출물에서 앱을 다시 실행하려 하지 말 것 — 기획서는 상태의 기록이지 앱이 아니다.
- localStorage는 임시 저장으로만 쓰고, 정본은 spec.json으로 목업 레포에 커밋한다.
- 기존 Draftify에서 계승하는 것은 코드가 아니라 산출물 규범과 실패의 교훈뿐이다 (§8).
  PPT는 산출물 범위에서 제외한다 — 탈 PPT가 이 프로젝트의 출발점이다.
