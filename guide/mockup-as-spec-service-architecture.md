# Mockup-as-Spec 서비스 설계 지침

> 작성일: 2026-07-06
> 선행 문서: [mockup-as-spec-guide.md](./mockup-as-spec-guide.md) — 편집 UX·앵커링·장면 동결 등 코어 개념
> 이 문서의 범위: 위 코어를 **"누구나 자기 목업을 가져오면 기획서 HTML을 만들어주는 서비스"**로
> 구성하는 방법 — 온보딩, 시스템 구성, 저장 모델, 보안, MVP 절단선
> 구현 사양: [s1-kickoff-spec.md](./s1-kickoff-spec.md) — S1 착수를 위한 확정 스펙

## 1. 서비스 정의

한 문장 정의:

> **각자가 이미 만든 목업(URL, 빌드 산출물, 레포)을 등록하면, 그 위에 어노테이션을 달아
> 단독 실행 가능한 기획서 HTML을 만들어 주는 사내 서비스.**

선행 가이드와의 관계가 바뀌는 지점이 핵심이다:

| | 선행 가이드 (도구 관점) | 이 문서 (서비스 관점) |
|---|---|---|
| SDK 주입 주체 | 목업 팀이 자기 레포에 한 줄 추가 | **서비스가 대신 주입** — 사용자는 목업을 수정하지 않음 |
| 목업 실행 위치 | 목업 팀의 dev 서버 | 서비스가 호스팅하거나 프록시 |
| spec 저장 | 목업 레포에 spec.json 커밋 | **서비스 서버가 보관** (레포 커밋은 옵션) |
| 사용자 전제 | 목업 레포 소유자 | 목업 레포를 못 고치는 사람 포함 (기획자, PM) |

"목업을 수정하지 않아도 된다"가 서비스의 존재 이유다. 이걸 지키는 것이 모든 설계 결정의
제1 기준이 된다.

## 2. 온보딩: 사용자가 목업을 가져오는 4가지 경로

서비스의 첫 화면은 "목업 등록"이고, 목업이 존재하는 형태별로 수용 경로를 나눈다.
**모든 경로의 종착점은 동일하다: "SDK가 주입된 상태로 서비스 도메인 아래에서 열리는 목업".**

### 경로 A. 정적 빌드 산출물 업로드 — MVP 기본 경로 ★

```
사용자: dist.zip 업로드 (npm run build 결과물)
서비스: 압축 해제 → 정적 호스팅 (/m/{projectId}/...) → index.html에 SDK <script> 자동 삽입
```

- 가장 단순하고 가장 견고. 백엔드 없는 순수 목업은 이걸로 끝
- SPA history 라우팅은 `/m/{projectId}/*` → `index.html` fallback으로 처리
- base path 문제(절대경로 `/assets/...`)는 업로드 시 재작성(rewrite)하거나,
  프로젝트별 서브도메인(`{projectId}.spec.internal`)으로 회피 — **서브도메인 방식 권장**
  (재작성은 JS 내부 문자열 경로까지 못 잡는다)

### 경로 B. URL 등록 → 리버스 프록시 래핑

이미 어딘가에 떠 있는 목업(사내 스테이징, Vercel 등)의 URL만 등록:

```
사용자: https://mockup.team-a.internal 등록
서비스: {projectId}.spec.internal → 해당 오리진으로 리버스 프록시
        HTML 응답에 SDK <script> 주입 (응답 스트림 변조)
```

- 목업이 자체 백엔드를 쓰고 있어도 그대로 동작 (프록시가 API 호출도 통과시킴)
- 같은 오리진이 되므로 iframe/postMessage 없이 SDK가 DOM에 직접 접근 가능
- 유의점은 §5(보안)에서: SSRF, 인증 쿠키 통과, CSP 헤더 제거

### 경로 C. 레포 연동 (git URL) — 후순위

서비스가 clone → build → 경로 A로 합류. 빌드 환경 다양성(node 버전, env 변수, 모노레포)
때문에 유지비가 크다. **M3 이후로 미룰 것.** 그전엔 "빌드해서 zip 올리세요"로 안내.

### 경로 D. 로컬 dev 서버 + 스니펫 — 탈출구

방화벽 안 로컬에서만 도는 목업용. 서비스가 발급한 프로젝트 토큰이 든 스크립트 한 줄
(또는 북마클릿)을 붙이면, SDK가 로컬 목업 위에서 뜨고 spec 데이터만 서비스 API로 저장.

```html
<script src="https://spec.internal/sdk.js" data-project="prj_abc123"></script>
```

- 이 경우만 예외적으로 목업 쪽에 한 줄 수정이 필요 — 선행 가이드의 B안이 이 경로로 흡수됨

### 경로 결정 플로우 (사용자에게 보여줄 것)

```
목업이 어디 있나요?
├─ 빌드 결과물(zip)을 만들 수 있다 ──▶ 경로 A (권장)
├─ 이미 URL로 접근 가능하다 ────────▶ 경로 B
├─ 로컬에서만 돈다 ────────────────▶ 경로 D
└─ 레포만 있다 ────────────────────▶ (당분간) 빌드해서 경로 A
```

## 3. 시스템 구성

```
┌─────────────────────────────────────────────────────────────┐
│                        사용자 브라우저                         │
│  {projectId}.spec.internal                                   │
│  ┌──────────────────────────────┬─────────────────────────┐  │
│  │  목업 (호스팅 or 프록시)       │  Spec Editor SDK        │  │
│  │                              │  (주입됨, Shadow DOM)    │  │
│  └──────────────────────────────┴───────────┬─────────────┘  │
└──────────────────────────────────────────────┼───────────────┘
                                               │ REST (spec CRUD)
        ┌──────────────────────────────────────▼─────────────┐
        │              Spec Service (Express)                 │
        │  ├─ Gateway/Injector: 정적 호스팅 + 프록시 + SDK 주입 │
        │  ├─ Spec API: 프로젝트/장면/어노테이션 CRUD           │
        │  ├─ Asset Store: 업로드 zip, 장면 스냅샷, 스크린샷    │
        │  ├─ Export: spec + 스냅샷 → 단독 HTML 번들링          │
        │  └─ 접근 제어: 사내망 + 비추측성 ID (§3.5, 인증 없음) │
        └────────────────────────────────────────────────────┘
```

구성 요소별 책임과 설계 지침:

### 3.1 Gateway/Injector
- 경로 A: 정적 파일 서빙 + HTML에 `<script src="/sdk.js">` 삽입
- 경로 B: 리버스 프록시 + 응답 HTML 변조 주입 + `Content-Security-Policy`/`X-Frame-Options`
  응답 헤더 스트립 (SDK 동작 방해 방지)
- **프로젝트별 서브도메인**으로 격리: 목업 간 localStorage/쿠키 오염 방지, base path 문제 회피

### 3.2 Spec Editor SDK
- 선행 가이드의 코어(마커, 패널, 장면, 앵커)를 그대로 사용하되, 저장 대상만 교체:
  localStorage(임시) → **Spec API(정본)**. 오프라인/네트워크 단절 시 localStorage 큐잉 후 재전송
- SDK는 단일 JS 파일로 빌드하여 4가지 온보딩 경로가 전부 동일 파일을 공유 — 서비스의
  핵심 재사용 단위

### 3.3 Spec API + 저장 모델

```
Project   { id, name, ownerId, members[], mockupSource: {type: upload|proxy|snippet, ...} }
Scene     { id, projectId, title, route, order, snapshotRef, screenshotRef }
Annotation{ id, sceneId, number, anchor{...}, title, description, policyRefs[], transition{...} }
Export    { id, projectId, createdAt, htmlRef, specVersion }   // 산출물 이력
```

- 저장소: 시작은 **파일 기반(JSON per project) 또는 SQLite**로 충분. 사내 도구에 DB 운영을
  먼저 얹지 말 것. 스키마는 선행 가이드 §6의 spec.json과 1:1 대응시켜 import/export가 곧
  백업이 되게 한다
- 장면 스냅샷(동결 DOM)은 크다(수 MB) → DB가 아니라 Asset Store(디스크/S3 호환)에 두고 참조만 저장

### 3.4 Export Service
- 장면 동결은 **클라이언트(SDK)에서 수행**해 서버로 업로드하는 것을 기본으로 한다.
  이유: 인증된 사용자의 브라우저에만 보이는 화면(로그인 후 상태)은 서버 헤드리스로 재현
  불가 — 기존 크롤러에서 이미 확인한 교훈
- Export는 서버에서 조립만: 저장된 스냅샷들 + spec 데이터 + 뷰어 템플릿 → 단일 HTML
- 뷰어 템플릿(장면 사이드바, 마커 렌더, 전이 링크, 흐름도)은 서비스가 관리하는 정적 자산
  → 템플릿 개선 시 기존 프로젝트도 재내보내기로 혜택

### 3.5 접근 제어 — 인증 없이 시작한다

기획서의 **소비(전달)에는 인증이 원천적으로 불필요하다**: 개발팀·유관팀은 서비스에
접속하지 않고 산출물 HTML 파일을 받아서 열 뿐이다. 인증이 관여할 수 있는 지점은 편집
측의 우발 사고(남의 프로젝트 수정·삭제) 방지뿐인데, 이는 보안 위협이 아니라 실수 방지
문제이므로 가벼운 수단으로 충분하다:

- 사내망 접근 제어 (전제)
- 비추측성 프로젝트 ID (편집 URL을 아는 사람만 접근)
- 삭제 시 확인 절차 + 작성자 이름 라벨 (인증이 아니라 표시)
- 민감 프로젝트는 내보내기 전 마스킹 단계(선행 가이드 §7.3)로 대응

**SSO 도입은 조건부**: 프로젝트가 수십 개·여러 부서로 확산되어 소유권 정리가 필요해지거나,
사내에서도 열람 제한이 필요한 목업(미공개 신사업 등)이 올라오거나, 수정 이력 추적이
요구될 때 — 그 전까지는 도입하지 않는다 (YAGNI).

## 4. 백엔드 연동 목업의 서비스 차원 처리

선행 가이드 §7의 "편집은 라이브, 산출물은 동결" 원칙은 그대로 유효하다. 서비스 관점에서
추가되는 것은 **편집 시점에 백엔드 붙은 목업을 어떻게 서비스 도메인 아래로 가져오나**:

| 목업 상황 | 경로 | 백엔드 처리 |
|-----------|------|------------|
| 백엔드 없음 (순수 프론트) | A (zip) | 해당 없음 |
| 백엔드 있음, URL 접근 가능 | B (프록시) | API 호출도 프록시 통과. 쿠키는 프록시 도메인으로 재바인딩 필요 (§5.2) |
| 백엔드 있음, 로컬에서만 | D (스니펫) | 사용자 로컬 환경 그대로 사용. 서비스는 spec 데이터만 수신 |
| 백엔드가 죽었거나 재현 불가 | — | 이미 동결된 장면은 계속 유효. 새 장면 추가만 불가 |

산출물은 어떤 경우든 동결 스냅샷 기반이므로 백엔드와 무관 — 서비스가 목업의 백엔드를
**호스팅하거나 모킹해줄 필요가 전혀 없다.** 이 선을 넘는 순간(예: "저희 백엔드도 띄워주세요")
서비스 범위 밖임을 명시할 것.

## 5. 보안 지침 (프록시 경로를 여는 순간 필수)

### 5.1 SSRF 방지
경로 B는 "사용자가 준 URL로 서버가 요청을 보내는" 구조 = 전형적 SSRF 표면.
- 허용 대상을 **사내 목업 대역/도메인 allowlist**로 제한 (deny-by-default)
- 클라우드 메타데이터 IP(169.254.169.254 등), 서비스 자신, 인프라 대역 차단
- 리다이렉트 추적 시에도 매 hop 재검증

### 5.2 인증 쿠키 통과
목업이 로그인을 요구하면, 프록시 도메인({projectId}.spec.internal)과 목업 도메인이 달라
쿠키가 안 붙는다.
- 기본 해법: 프록시가 `Set-Cookie`의 Domain 속성을 프록시 도메인으로 재작성
- SSO 콜백 URL 문제 등으로 안 풀리는 목업은 **경로 D로 우회 안내** — 모든 인증 체계를
  프록시로 뚫으려 하지 말 것 (비용 대비 무익)

### 5.3 주입 SDK의 권한 경계
- SDK는 목업 페이지의 DOM 전체에 접근한다 — 즉 목업이 다루는 데이터를 볼 수 있다.
  SDK가 서버로 보내는 것은 spec 데이터와 사용자가 명시적으로 동결한 스냅샷뿐임을
  코드 리뷰 기준으로 못 박을 것 (텔레메트리로 DOM을 흘리지 않기)
- 산출물/스냅샷에 실데이터가 포함되는 문제는 선행 가이드 §7.3의 마스킹으로 대응

## 6. MVP 절단선: 무엇부터 만들 것인가

서비스판 로드맵 (선행 가이드의 M1~M3와 병렬 개념이 아니라, 이것이 서비스 버전의 실행 계획):

### S1 — "업로드하면 편집되고 내보내진다" (최소 서비스)
- 경로 A만: zip 업로드 → 정적 호스팅 + SDK 주입
- Spec API (파일 기반 저장), SSO 없이 사내망 접근 제어만
- SDK: 마커 + 패널 + 장면 동결 + 단독 HTML 내보내기
- **검증 질문**: "남이 만든 목업을 목업 팀 도움 없이 기획서로 만들 수 있는가"

### S2 — "떠 있는 목업도 된다"
- 경로 B (프록시 + 주입 + SSRF allowlist + 쿠키 재바인딩)
- 경로 D (스니펫/토큰)
- 작성자 라벨·산출물 이력 (인증 없음 — §3.5)
- 다중 장면 + 전이 + 흐름도 자동 생성 (선행 가이드 M2 코어 합류)

### S3 — 보조 자동화·확장
- LLM 디스크립션 초안 제안 (신규 소형 구현 — 선행 가이드 §8. 기존 코드 재활용 아님)
- 레포 연동 빌드 (경로 C)
- SSO 등 인증 도입 검토 (§3.5의 조건 충족 시에만)

### 명시적 non-goal (서비스 범위 선언)
- **PPT 등 HTML 외 산출물 형식** — 탈 PPT가 프로젝트 출발 동기. 산출물은 단독 HTML 하나
- 크롤러 기반 장면 자동 시딩 — 서버 헤드리스 재현 금지(§3.4)와 모순, 선행 가이드 §8
- 목업의 백엔드 호스팅/모킹 대행 (§4)
- 실시간 동시 편집 (S2까지는 프로젝트당 편집자 1인 규칙)
- 사외 공개 호스팅 (사내망 전제 — 산출물 HTML이 유일한 사외 반출 수단)

## 7. 기존 Draftify 코드베이스와의 관계 — 코드 재활용 없음

> 2026-07-06 개정: 초판의 재활용 표(Express 뼈대, draftify-ui, 크롤러 시딩, LLM 초안,
> PPT export)는 철회한다. 기존 파이프라인의 비효율은 코드가 아니라 실행 방식(다단계 LLM
> 문서 생성, 헤드리스 크롤링)의 문제였고 그 실행 방식이 폐기 대상이므로, 이식할 코드가
> 없다. 서비스는 목업의 환경을 통제하지 않으므로(호스팅/프록시만 제공) 크롤러의 전제도
> 성립하지 않는다.

계승하는 것은 두 가지뿐:

- **산출물 규범**: `docs/design/auto-draft-guideline.md`의 섹션 구조·ID 체계 (POL-*, SCR-*)
- **실패의 교훈**: 자동 추론 금지, 서버 헤드리스 재현 금지, SPA 상태 자동 감지 의존 금지

전 컴포넌트를 새로 얇게 세운다 (기술 결정은 [s1-kickoff-spec.md](./s1-kickoff-spec.md) §2).
기존 파이프라인 코드를 끌어들이지 말 것 — 다른 문제를 풀던 코드다.

## 8. 결론

- "각자의 목업을 기획서 HTML로" = **주입을 서비스가 대신 해주는 것**이 도구와 서비스의
  본질적 차이. 사용자는 목업을 한 줄도 수정하지 않는다 (경로 D 제외).
- 온보딩은 4경로(zip 업로드 / URL 프록시 / 로컬 스니펫 / 레포 빌드) 중 **zip 업로드부터**.
  프록시는 보안(SSRF, 쿠키) 숙제와 함께 S2에서.
- 서비스가 새로 지는 책임은 Gateway/Injector, Spec API(서버 저장), Export 조립, 권한.
  편집 코어(SDK)와 산출물 원리(장면 동결)는 선행 가이드 그대로다.
- 백엔드 붙은 목업도 서비스가 백엔드를 대신 띄워줄 필요 없음 — 편집은 프록시/로컬로
  라이브하게, 산출물은 동결로. 이 선이 서비스 범위를 지키는 경계선이다.
