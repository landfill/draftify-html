## 1. 제품 정의

### 1.1 한 문장 정의

> **각자가 이미 만든 목업(zip 빌드 산출물, URL, 로컬 dev 서버)을 등록하면, 그 위에
> 숫자 어노테이션을 달아 단독 실행 가능한 기획서 HTML을 만들어 주는 사내 서비스.**

### 1.2 핵심 개념 (용어 정의)

| 용어 | 정의 |
|------|------|
| **목업(Mockup)** | 팀이 이미 만들어 둔 동작하는 화면. 정적 빌드 산출물, 배포된 URL, 로컬 dev 서버 등 어떤 형태든 무방 |
| **어노테이션(Annotation)** | 목업의 인터랙션 요소(버튼, 입력창 등)에 부착하는 숫자 마커 + 기획 설명. 사람이 직접 작성 |
| **장면(Scene)** | URL이 아니라 "사람이 의미를 부여한 화면 상태"(모달 열림, 탭 선택, 검색 결과 표시 등). 작성자가 명시적으로 선언하며, 어노테이션은 항상 특정 장면에 소속됨 |
| **앵커(Anchor)** | 어노테이션을 목업 요소에 붙이는 다중 시그니처(CSS 셀렉터 + 텍스트 + 접근성 속성 + 비율 좌표). 리렌더·반응형에서도 마커가 살아남게 하는 장치 |
| **장면 동결(Scene Freeze)** | 장면 등록 시점에 렌더 완료된 DOM을 통째로 직렬화(CSS 인라인, 이미지 data URI화, 스크립트 제거)하는 것. 산출물이 백엔드 없이 동작하게 하는 핵심 메커니즘 |
| **전이(Transition)** | "이 요소를 조작하면 → 장면 X로 이동"이라는, 작성자가 지정하는 장면 간 연결. 프로세스 흐름도의 원천 데이터 |
| **산출물(Export)** | 장면 스냅샷 + 어노테이션 + 뷰어를 하나로 묶은 **단일 HTML 파일**. `file://`로 열리고 네트워크가 전혀 필요 없음 |
| **Mockup-as-Spec / Living Spec** | 목업 자체가 기획서가 된다는 제품 철학. 별도 문서를 만드는 게 아니라 목업 위에 의도를 기록 |

### 1.3 제품 철학 (설계 제1원칙)

1. **의도는 추론하지 않고, 사람이 입력한다.** 기획 의도는 목업 밖(사람 머릿속)에 있으므로 역공학(크롤링 + LLM 추론)으로 복원할 수 없다. **기본 원칙은 LLM 미사용**이며, 유일한 LLM 기능(디스크립션 초안 제안, S3)도 옵트인 — 기본 OFF, 설정에서 켠 경우에만 동작하고 최종 확정은 항상 사람이 한다.
2. **사용자는 목업을 수정하지 않는다.** SDK 주입은 서비스가 대신 한다. 이것이 도구가 아닌 "서비스"의 존재 이유이며, 모든 설계 결정의 제1 기준.
3. **편집은 라이브, 산출물은 동결.** 편집 시점엔 백엔드가 있어도 되고, 산출물 시점엔 백엔드가 필요 없다. 기획서는 상태의 기록이지 앱이 아니다.
4. **서버 헤드리스 재현 금지.** 로그인 후 화면 등 인증된 사용자의 브라우저에만 보이는 상태는 서버가 재현할 수 없다. 동결은 반드시 사용자 브라우저에서 수행한다.

## 2. 배경과 문제 정의

### 2.1 기존 파이프라인(Draftify: 크롤링 → LLM 분석 → PPT 생성)의 한계

| # | 문제 | 근본 원인 |
|---|------|----------|
| P1 | 프로세스 흐름도가 제대로 생성되지 않음 | 흐름(전이) 정보는 DOM에 존재하지 않음. LLM이 추측으로 채움 |
| P2 | SPA 버튼 클릭/화면 전환을 헤드리스로 구분 불가 | "사람이 의미를 부여한 상태 전이"를 크롤러가 알 수 없음 |
| P3 | 디스크립션이 부정확한 정보로 채워짐 | 스크린샷 → LLM 역추론은 원래 기획 의도를 복원 못함 |
| P4 | 작은 서비스에도 10분+ 소요 | 크롤링 + 다단계 LLM 호출의 순차 파이프라인 |
| P5 | AI API 과다 사용, 저가 모델 전환 시 품질 저하 | 전체 산출물을 LLM 생성에 의존하는 구조 |

**공통 근본 원인**: 기획 의도를 역공학으로 추론하려 했기 때문.

### 2.2 새 방향이 문제를 해소하는 방식

| 기존 문제 | 해소 메커니즘 |
|-----------|--------------|
| P1 흐름도 부정확 | 사람이 입력한 전이(transition) 데이터의 결정론적 렌더링 (자체 경량 SVG — 2026-07-12 Mermaid에서 변경, s1-kickoff §11 7차). LLM 불필요 |
| P2 SPA 상태 감지 실패 | 사람이 장면을 선언. 라우트 변경 감지는 "제안" 트리거로만 사용 |
| P3 디스크립션 부정확 | 의도를 아는 사람이 직접 입력. LLM은 (S3에서) 초안 제안만 |
| P4 10분+ 소요 | 크롤링 자체가 없음. 장면 등록은 버튼 한 번 |
| P5 LLM 비용/품질 | LLM이 산출물 생성 경로에서 제거됨 |

### 2.3 기존 Draftify 자산과의 관계 — 코드 재활용 없음 (확정)

기존 파이프라인의 비효율은 코드가 아니라 실행 방식(다단계 LLM 생성, 헤드리스 크롤링)의 문제였고, 그 실행 방식 자체가 폐기 대상이므로 이식할 코드가 없다. 계승하는 것은 두 가지뿐:

- **산출물 규범의 원칙**: "섹션 구조와 ID 체계를 규범으로 관리한다"는 원칙만 계승한다. 기존 `docs/design/auto-draft-guideline.md` 문서 자체는 가져오지 않으며, 체계(SCR-\*, POL-\* 등)는 mockspec 데이터 모델에 맞게 [output-standard.md](./output-standard.md)에서 **신규 설계**한다. 어노테이션의 `policyRefs` 필드가 기존 사내 정책 문서와의 연결 고리
- **실패의 교훈**: 자동 추론 금지 · 서버 헤드리스 재현 금지 · SPA 상태 자동 감지 의존 금지

## 3. 목표 사용자와 사용 시나리오

### 3.1 페르소나

| 페르소나 | 설명 | 핵심 니즈 |
|----------|------|----------|
| **기획자/PM (주 사용자)** | 목업 레포를 못 고치는(고치고 싶지 않은) 사람. 기획서 작성 책임자 | 목업 팀 도움 없이 기획서를 만들고 싶다 |
| **프론트엔드 개발자** | 목업 제작자. 자기 목업이 어떻게 쓰이는지 알고 싶은 사람 | 기획서 갱신 요청에 시달리지 않고 싶다 |
| **산출물 소비자 (개발팀·유관팀·경영진)** | 서비스에 접속하지 않음. HTML 파일을 받아서 열 뿐 | 설치·로그인 없이 어디서나 열리는 기획서 |

### 3.2 핵심 사용 시나리오 (S1 기준)

```
1. 기획자가 개발팀에서 받은 빌드 결과물(dist.zip)을 콘솔에 업로드
2. 서비스가 목업을 호스팅하고 SDK를 주입 → 전용 URL에서 목업이 열림
3. 기획자가 목업을 조작해 원하는 화면 상태를 만들고 [+ 현재 화면을 장면으로] 클릭
4. 편집 모드에서 버튼·입력창을 클릭 → 숫자 마커 부착 → 우측 패널에서 설명 입력
5. export 버튼 → 단독 실행 HTML 다운로드
6. 메일/위키로 공유 → 받는 사람은 file://로 열어서 열람 (네트워크 0건)
```

### 3.3 검증 질문 (S1 게이트)

> **"남이 만든 목업을 목업 팀 도움 없이 기획서로 만들 수 있는가"**

S1 종료 시 실사용 1회(팀 내 실제 목업으로 기획서 1부 완성)로 판정하고 결과를 기록한다.

## 4. 핵심 프로세스

### 4.1 전체 프로세스 개요

```
[온보딩]           [편집]                    [산출]              [소비]
목업 등록    →    장면 선언 + 어노테이션   →   단일 HTML 조립   →   file://로 열람
(zip/URL/스니펫)   + 장면 동결(브라우저에서)    (서버는 조립만)      (백엔드·네트워크 불필요)
```

### 4.2 프로세스 1 — 온보딩: 목업 등록 (4가지 경로)

모든 경로의 종착점은 동일: **"SDK가 주입된 상태로 서비스 도메인 아래에서 열리는 목업"**

| 경로 | 대상 | 방식 | 단계 |
|------|------|------|------|
| **A. zip 업로드** ★ | 정적 빌드 산출물을 만들 수 있는 목업 | 압축 해제 → 정적 호스팅 → SDK 자동 삽입 | **S1** |
| **B. URL 프록시** | 이미 URL로 접근 가능한 목업 (스테이징 등) | 리버스 프록시 + 응답 HTML에 SDK 주입 | S2 |
| **C. 레포 빌드** | git URL만 있는 목업 | clone → build → 경로 A 합류 | S3 |
| **D. 클라이언트 주입 (확장)** | 로그인 뒤에만 보이는 화면(SSO 포함), 로컬에서만 도는 목업 | 브라우저 확장(content script)이 **사용자 세션 위에** SDK 주입, 저장은 프로젝트 토큰 인증 — 목업 수정 없음 | S2.5 |

경로 D 방식 변경(2026-07-11): "스니펫 한 줄 부착"에서 **브라우저 확장**으로 확정 —
경로 B 실사용에서 "직접 로그인해 둔 화면을 쓰고 싶다"는 실수요가 확인됐고, CSP가 엄격한
로그인 실화면은 스니펫으로 뚫리지 않는다. 상세·WBS·DoD는
[guide/pathD-kickoff-spec.md](../guide/pathD-kickoff-spec.md).

사용자 안내 플로우:

```
목업이 어디 있나요?
├─ 빌드 결과물(zip)을 만들 수 있다 ──▶ 경로 A (권장)
├─ 이미 URL로 접근 가능하다 ────────▶ 경로 B
├─ 로그인해야 보인다 / 로컬에서만 돈다 ─▶ 경로 D (확장)
└─ 레포만 있다 ────────────────────▶ (당분간) 빌드해서 경로 A
```

### 4.3 프로세스 2 — 편집: 장면 선언과 어노테이션

1. **장면 선언 (사람이 주도)**: 작성자가 목업을 원하는 상태로 조작한 뒤 [+ 현재 화면을 장면으로] 클릭. SDK가 그 순간을 등록하고 즉시 동결. SPA 라우트 변경은 "새 장면으로 등록할까요?" **제안**만 — 자동 생성 금지.
2. **어노테이션 부착**: 편집 모드에서 요소 클릭 → 번호 자동 부여 + 앵커 자동 생성 → 패널에서 title/description 입력. 목업을 조작해야 할 땐 미리보기 모드로 전환.
3. **자동 저장**: 변경은 500ms 디바운스로 Spec API에 저장. 오프라인 시 localStorage 큐잉 후 재전송.
4. **(S2) 전이 지정**: 어노테이션에 "→ 장면 X로 이동" 지정 → scenes + transitions가 방향 그래프가 되어 프로세스 흐름도로 자동 렌더.

### 4.4 프로세스 3 — 산출: 단독 HTML 내보내기

- 동결은 이미 편집 중에 완료됨 (클라이언트 브라우저에서). 서버는 저장된 스냅샷들 + spec 데이터 + 뷰어 템플릿을 **조립만** 한다.
- 산출물은 단일 .html 파일: 장면 사이드바 + 동결 DOM 뷰어(읽기 전용) + 어노테이션 마커/패널 + (S2) 전이 링크·흐름도.
- `file://`로 열리고 네트워크 요청 0건. 목업이 나중에 죽어도 산출물은 그 시점 상태를 보존 (아카이브 속성).

### 4.5 프로세스 4 — 소비: 산출물 열람

- 소비자는 서비스에 접속하지 않는다. HTML 파일을 받아 열 뿐 — **소비에는 인증이 원천적으로 불필요**.
- 뷰어 템플릿은 서비스가 관리 → 템플릿 개선 시 재내보내기로 기존 프로젝트도 혜택.

### 4.6 백엔드 연동 목업 처리 (판단 기준)

| 목업 상황 | 경로 | 백엔드 처리 |
|-----------|------|------------|
| 백엔드 없음 (순수 프론트) | A | 해당 없음 |
| 백엔드 있음, URL 접근 가능 | B | API 호출도 프록시 통과. 쿠키 재바인딩 |
| 백엔드 있음, 로컬에서만 | D | 사용자 로컬 환경 그대로. 서비스는 spec 데이터만 수신 |
| 백엔드가 죽었거나 재현 불가 | — | 동결된 장면은 계속 유효. 새 장면 추가만 불가 |

서비스가 목업의 백엔드를 호스팅하거나 모킹해주지 않는다 — 이 선이 서비스 범위의 경계선.

## 5. 기능 요구사항

우선순위: **P0** = S1 필수, **P1** = S2 이후, **P2** = S3.

P1 중 **S2 확정 범위는 FR-ONB-05(경로 B)와 FR-EDT-11(마스킹)뿐**이다 (2026-07-10, §7.1).
**FR-ONB-06(경로 D)은 S2 종료 후 실수요 확인으로 S2.5 확정**(2026-07-11, §7.1).
**FR-EDT-10·FR-EXP-06(전이 지정 + 흐름도)은 S2.5 종료 후 사용자 우선순위 결정으로 착수 확정**(2026-07-12, §7.1 후속 판단).
나머지 P1(FR-EDT-12, FR-EXP-08, FR-CON-03)은 실수요를 보고 판단한다.

### 5.1 온보딩·호스팅

| ID | 요구사항 | 우선순위 |

## 6. Non-Goals (명시적 범위 제외)

로드맵 전체(S1~S3)에서 구현하지 않는다:

1. **PPT 등 HTML 외 산출물 형식** — 탈 PPT가 프로젝트 출발 동기. 산출물은 단독 HTML 하나
2. **크롤러 기반 장면 자동 시딩** — 서버 헤드리스 재현 금지 원칙과 모순
3. **목업의 백엔드 호스팅/모킹 대행** — "저희 백엔드도 띄워주세요"는 범위 밖임을 명시
4. **실시간 동시 편집** — S2까지 프로젝트당 편집자 1인 규칙
5. **사외 공개 호스팅** — 사내망 전제. 산출물 HTML이 유일한 사외 반출 수단
6. **기존 Draftify 코드 이식** — §2.3
7. **모바일 편집 환경** — 뷰포트별 장면 동결로 모바일 "표현"은 가능하되 편집은 PC 전제
8. **산출물에서의 실제 앱 실행** — 장면 동결 + 전이 링크로 대체

### 7.2 SSO 도입 조건 (그 전까지 YAGNI)

다음 중 하나가 충족될 때만 검토: ① 프로젝트가 수십 개·여러 부서로 확산되어 소유권 정리가 필요, ② 사내에서도 열람 제한이 필요한 목업(미공개 신사업 등) 등장, ③ 수정 이력 추적 요구.

### 7.3 S1 Definition of Done

Playwright 자동화 단일 시나리오 통과 + 실사용 1회 판정 기록:

1. 샘플 SPA 목업(Todo 앱) zip 업로드
2. 장면 2개 등록, 어노테이션 각 2개 부착·설명 입력
3. export → 산출물 HTML을 새 브라우저 컨텍스트에서 `file://`로 오픈
4. 검증: 장면 2개 전환 가능, 마커 4개가 올바른 요소 위에 표시, 설명 텍스트 일치, **네트워크 요청 0건**

### 7.4 성공 지표

| 지표 | 목표 |
|------|------|
| 기획서 1부 완성 소요 시간 | 기존 파이프라인(10분+ 자동 생성 후 수정) 대비, 편집 포함 총 소요가 체감상 우위 (S1 실사용에서 판정) |
| 목업 팀 개입 횟수 | 0회 (경로 A·B 기준) |
| 산출물 정확도 | 흐름도·디스크립션에 추측 정보 0건 (구조적으로 보장 — 사람 입력만 렌더) |
| LLM API 비용 | 산출물 생성 경로에서 0원. S3 초안 제안은 옵트인(기본 OFF)이므로 켜지 않은 프로젝트는 전 구간 0원 |
