# UI 규범 — 표면별 인벤토리와 공통 시각 기준

> 지위: **UI 규범.** 네 표면(공개판·사내판·SDK 편집 패널·산출물)의 현재 시각 스타일을
> 기록하고, 앞으로 따를 공통 기준을 정한다. 이슈 #87의 산출물이다.
>
> 이 문서는 **무엇이 어떻게 생겼는지**를 다룬다. **무엇을 보여줄지**(정보 구조·우선순위)는
> [detailed-spec.md](./detailed-spec.md)가, **산출물의 ID 체계·섹션 구조**는
> [output-standard.md](./output-standard.md)가 정본이다. 충돌하면 그쪽이 이긴다.

## 0. 범위와 경계

| | 이 문서 | 다른 곳 |
|---|---|---|
| 공개판 첫 화면·콘솔 홈의 **정보 구조** | ✗ | 이슈 #85 (완료) |
| 산출물의 **레이아웃·스크롤·네비 중복** | ✗ | 이슈 #86 (착수 대기) |
| 산출물의 **ID 체계·섹션 구조** | ✗ | `output-standard.md` · `s1-kickoff-spec.md` |
| 네 표면의 **색·타이포·간격·상태·포커스** | ✓ | — |

**산출물(`packages/server/src/routes/export.ts`)의 시각 스타일은 이번 범위에서 인벤토리만
기록하고 코드는 바꾸지 않는다** (2026-08-02 사용자 결정). 이유는 **일정과 절차**다:

1. **#86이 같은 파일의 레이아웃을 갈아엎을 예정**이라, 지금 색을 건드리면 확정적으로 충돌한다
2. 산출물의 섹션 구조·ID 체계는 `output-standard.md`·`s1-kickoff-spec.md`의 계약이라
   레이아웃을 넘어서면 AGENTS.md 4절 절차(킥오프 문서 → 결정 변경 이력 → docs 동기화)가 선행한다

> **"네트워크 0건이라 토큰을 공유할 수 없다"는 이유는 틀렸다** (PR #89 리뷰에서 정정).
> 초안에 그렇게 적었으나 **런타임 요청과 빌드타임 import를 혼동한 것**이다.
> `export.ts`는 `packages/server` 안에서 돌고 이미 `@mockspec/shared`를 import하며
> (`export.ts:3`), CSS를 `<style>${VIEWER_CSS}</style>`로 문자열 보간해 내보낸다.
> 따라서 **4.7절의 `THEME_TOKENS`를 import해 값을 그 문자열에 구워 넣을 수 있고,
> 결과 HTML은 그대로 네트워크 요청 0건이다.**
>
> 이 정정이 중요한 이유: 틀린 이유를 남겨 두면 #86이 팔레트를 손으로 재복제하게 되고,
> 그것은 이 문서가 F-02로 지적한 드리프트를 한 곳 더 만드는 일이다.
> **산출물에 시각 언어를 입힐 때는 빌드타임 재사용을 기본으로 삼는다.**

따라서 산출물은 **#86에서 구조가 확정된 뒤 그 위에 시각 언어를 입힌다.**

### 1.2 측정값 — 스케일의 부재

파일별로 실제 등장하는 서로 다른 값의 개수다. 스케일이 있다면 이 숫자가 작아야 한다.

**측정 방법**: `font-size: <숫자>px` 선언의 서로 다른 값을 센다. 반응형
`font-size: clamp(...)`는 값이 뷰포트에 따라 연속이라 같이 셀 수 없으므로 **선언 건수와
상한만 따로** 적는다. 랜딩 제목이 최대 58px까지 커지는 것이 이 행에 잡힌다 — 고정값
행의 상한(22px)만 보고 "이 파일의 최대 글자가 22px"로 읽으면 안 된다.

| | 공개판 | 사내판 콘솔 | SDK 패널 | 산출물 |
|---|---|---|---|---|
| `font-size` 고정값 종류 | **16종** (6.5→22px) | 6종 (10→13px) | 6종 (11→22px) | 6종 (12→18px) |
| `font-size` 반응형(`clamp`) | **4건** (상한 38·42·48·58px) | 0 | 0 | 0 |
| `border-radius` 종류 | **9종** (4·5·6·7·8·10·12·16·999px) | 5종 | **7종** (3·4·5·6·7·8·10px) | 4종 |
| `gap` 종류 (공개판) | **17종** (1·4·5·6·7·8·9·10·12·14·16·18·20·22·24·32·54px) | — | — | — |
| `box-shadow` 선언 | 10건 | 3건 | 4건 | 2건 |

공개판의 고정값 16종 중 6.5~9px 구간은 **랜딩의 코드로 그린 제품 미리보기**
(`.l-preview-*`, `pointer-events: none`, 컨테이너에 `aria-label` + 내부 `aria-hidden`)에만
쓰인다. 본문이 아니라 삽화이므로 본문 스케일 위반으로 세지 않는다 — 다만 삽화가 본문과
같은 CSS 네임스페이스에 섞여 있어 통계를 왜곡한다는 점은 남는다.

SDK의 반경 7종(3·4·5·6·7·8·10px)은 사실상 연속값이다. 3px와 4px, 6px와 7px의 차이는 화면에서
구별되지 않으므로 **의미 없는 변이**다.

> **이 표는 PR #89 적용 후에도 그대로다.** 로그인·히어로를 고치면서 새 값을 만들지 않고 이미
> 있던 값(제목 22px, 부제·버튼·입력 13px, 히어로 gap 54px)을 재사용했기 때문이다. 초안에서는
> 24px·13.5px·56px를 새로 넣어 종류가 16→18, 17→18로 늘었는데, **그것이 바로 4.2절이 금지하는
> 행위**라 되돌렸다 (PR #89 리뷰). 값을 하나 더 만들기 전에 이 표를 먼저 본다.

## 2. 확인된 결함

측정·계산으로 검증한 것만 적는다. 인상 비평은 3절에 따로 둔다.

### F-01 `--c-faint`가 라이트·다크 양쪽에서 WCAG AA 미달 (본문 텍스트) — **해소 (2026-08-02)**

> **해소됨 — `--c-faint`를 삭제하고 `--c-muted`로 통합했다** (Q-04 결정, T87-10).
> 아래는 결함의 원 기록이다. 사용처 4곳은 전부 `--c-muted`를 쓰고, 토큰 자체가 없어졌으므로
> **이 값이 다시 낮아질 자리도 없다.** 통합 후 대비는 라이트 4.76:1 / 다크 5.71:1로 둘 다 AA를
> 통과한다. 적용 상세는 6.3절.

WCAG 2.1 SC 1.4.3은 일반 텍스트에 4.5:1을 요구한다. 계산 결과:

| 조합 | 대비 | 판정 |
|---|---|---|
| 라이트 `#94a3b8` on `#fff` | **2.56:1** | ✗ 미달 |
| 다크 `#64748b` on `#1e293b` | **3.07:1** | ✗ 미달 (큰 텍스트 기준 3:1만 충족) |

이 토큰이 쓰이는 곳은 전부 **11px 일반 텍스트**다 — 큰 텍스트 예외를 받을 수 없다:

- `.c-project-meta` — 프로젝트 목록의 생성일·내보내기 횟수 (`globals.css:690`, `console.ts:65`)
- `.c-extension-steps li::before` — 확장 설치 절차 번호 (`globals.css:511`)
- `.g-path dt` — 가이드의 **정의 목록 용어** (`pages.ts:104`)
- `.g-faq-item summary::before` — FAQ 펼침 표시 (`pages.ts:138`)

공개판·사내판 양쪽에 동시에 존재한다. 대조군으로 같은 팔레트의 다른 토큰은 통과한다
(`--c-muted` 라이트 4.76:1 / 다크 5.71:1, `--c-text-3` 7.58 / 9.85, `--c-accent` 6.29 / 7.34).
즉 **팔레트 전체가 아니라 `--c-faint` 한 토큰의 문제**다.

### F-02 토큰 블록이 두 파일에 손으로 복제돼 있다

`apps/web/app/globals.css`의 `:root` / `:root[data-theme="dark"]` 블록과
`packages/server/src/routes/shell.ts`의 같은 블록을 선언 단위로 정렬해 대조한 결과
(2026-08-02 실측):

| 블록 | 공개판 선언 수 | 사내판 선언 수 | 차이 |
|---|---|---|---|
| `:root` (라이트) | 30 | 28 | 공개판에만 `--c-label-w`·`--c-row-gap` |
| `:root[data-theme="dark"]` | 28 | 28 | **없음 — 전부 일치** |

> **T87-10 이후 각 블록에서 `--c-faint` 한 줄이 빠졌다** (라이트 29/27, 다크 27/27).
> 차이의 구조는 그대로다 — 여전히 레이아웃 토큰 2종만 다르다.

즉 다크 블록은 완전히 같고, 라이트 블록도 **레이아웃 토큰 2종을 빼면 완전히 같다.** 그 2종은
사내판이 `console.ts:17-18`의 별도 `:root`에 같은 값(`120px`·`10px`)으로 둔다 — 값이 다른 게
아니라 **선언 위치만 다르다.**

지금 일치한다는 것이 안전을 뜻하지 않는다. **한쪽만 고치면 조용히 갈라지고, 그걸 잡아주는
테스트가 없다.** F-01을 고치는 순간 바로 이 위험에 노출된다 — 두 파일을 다 고쳐야 한다.

### F-03 포커스 표시가 표면마다 다르다

`:focus-visible` 선언 건수:

| 표면 | 건수 | 어디에 |
|---|---|---|
| 공개판 `globals.css` | 4 | 탭 · 생성 패널 요약 · 생성 피드백 · 가이드 용어 복사 버튼 |
| 사내판 | 1 | `pages.ts` 1건. `shell.ts`·`console.ts`(931줄)·`sample.ts`는 **0건** |
| SDK `styles.ts` | **0** | — |
| 산출물 `export.ts` | **0** | — |

저장소 전체에서 `outline: none`은 3곳뿐이고, 셋 다 대체 표시가 있다 — `globals.css:417`과
`console.ts:35`는 입력 필드에 `box-shadow` 링을 주고, `globals.css:217`의
`.c-creation-feedback { outline: none }`은 바로 아래 `:224`의
`.c-creation-feedback:focus-visible .c-status`가 `outline` 링으로 받는다.
**포커스를 지우기만 한 곳은 없다.**
SDK와 산출물은 선언 자체가 없어 브라우저 기본 링이 그대로 보인다. 즉 **접근성 실패는 아니다.**

문제는 일관성이다. 같은 제품 안에서 포커스가 세 가지로 보인다:

1. 인디고 2px `outline` + 2px offset — 공개판의 탭·요약·복사 버튼
2. 3px `box-shadow` 링 + 테두리 색 변화 — 공개판·사내판의 입력 필드
3. 브라우저 기본 링 — 사내판 콘솔의 버튼·링크 전부, SDK 전부, 산출물 전부

완료 조건의 "포커스 표시가 유지된다"는 충족하지만 "같은 역할의 UI 요소가 화면별로 불필요하게
다른 형태를 쓰지 않는다"에는 걸린다.

### F-04 본문 크기 단위가 표면마다 다르다 (사용자 글꼴 설정 존중 여부)

산출물만 `font-size: 81.25%`로 **상대값**을 쓴다. 브라우저 기본 글꼴 크기를 키운 사용자에게
비례해 커진다 — 의도된 설계이고 `export.ts:14-16`에 리뷰 반영 근거가 주석으로 남아 있다.

반면 공개판·사내판 콘솔은 `body { font-size: 11.5px }` **절대값**이라 사용자 설정을 무시한다.
SDK도 `13px` 절대값이다. 셋 중 산출물의 방식이 옳고, 나머지가 그 기준에서 벗어나 있다.

### F-05 사내판 콘솔과 SDK 패널에 반응형 규칙이 사실상 없다

`@media` 선언은 사내판 전체에서 `shell.ts:142`의 720px 하나뿐이고, `console.ts`(931줄)와
SDK `styles.ts`에는 0건이다. SDK 패널은 `width: 360px` 고정이라 390px 뷰포트에서 화면의
92%를 덮는다. 완료 조건의 "390px 이상에서 가로 넘침 없음"은 **미검증 상태**다 — 이 문서는
규칙의 부재만 기록하고, 실제 넘침 여부는 적용 단계에서 실측한다.

## 3. 진단 — 읽는 화면에 도구 화면의 밀도를 그대로 썼다

### 3.0 A/B로 기각된 가설 — **글자를 키우는 방향은 두 번 기각됐다**

> **다음 세션은 이 절을 먼저 읽는다.** 같은 가설을 다시 세우지 않기 위한 기록이다.

| 회차 | 가설 | 실험 | 판정 |
|---|---|---|---|
| 1 | 콘솔에 타이포 대비가 없어서 전 화면이 밋밋하다 → 본문 14px·제목 20px | `console-ab.html` | **기각** — "원래 화면이 더 낫다" |
| 2 | 읽는 화면(로그인·가이드·FAQ)에 도구 밀도를 써서 그렇다 → 본문 15px·줄 45자 | `reading-ab.html` | **부분 기각** — 가이드·FAQ는 현재가 낫다. **로그인만 채택** |
| 3 | 랜딩 히어로 미리보기가 빈 와이어프레임이라 미완성으로 보인다 → 내용을 채운다 | `cmp-hero.png` | **기각** — "안 채우는 게 낫다" |
| 4 | 랜딩의 자잘한 불일치를 정돈하면 나아진다 (본문 크기 4종→2종 등) | `cmp-flow.png` | **철회** — 렌더 결과 **보이는 차이가 없었다.** 코드 위생이지 디자인 개선이 아니다 |
| 5 | 히어로를 중앙 정렬 1단으로 | `cmp-center-wide.png` | **채택** |

**4회차에서 배운 것(방법론):** 인터랙티브 A/B 페이지(`*-ab.html`)는 창 폭이 좁으면 두 패널이
세로로 쌓이고 iframe이 2600px라 **나란히 비교가 불가능했다.** 사용자가 "차이를 모르겠다"고 한
주된 원인이 디자인이 아니라 이 비교 도구였다. 이후로는 **Playwright로 실제 앱을 띄워 찍은 정지
이미지**를 나란히 놓고 본다. 절차는 7.1절에 있다.

> 위 표의 산출물(`console-ab.html`·`cmp-hero.png` 등)은 **판단 근거로 쓰고 버린 임시
> 파일이라 저장소에 없다.** 결론만 이 표에 남긴다 — 다시 확인하려면 7.1절 절차로 새로 찍는다.

**확립된 사실: 이 제품에서 본문 글자 크기를 키우는 방향은 채택되지 않는다.** 현재 밀도가
사용자의 선호다. 앞으로 어떤 화면에도 "본문을 키워 위계를 만든다"를 기본 처방으로 쓰지 않는다.

로그인만 채택된 이유가 방향을 알려 준다. 로그인 B가 고친 것은 **밀도가 아니라 구조적 결함**
이었다 — 13px짜리 `<h1>`, 위계 없는 동일 버튼 2개, 인라인 `style`로 콘솔 폼 그리드를 되돌리던
땜질, 서비스 설명 부재. 반면 가이드·FAQ B는 **주로 크기를 키웠고**, 그래서 기각됐다.

> **그래서 판단 기준은 이것이다: 고치는 것이 "구조적 결함"인가, 아니면 "밀도 취향"인가.**
> 전자만 손댄다.

### 3.1 화면 성격 구분 (참고용 — 처방이 아니다)

| 성격 | 화면 | 현재 판정 |
|---|---|---|
| **도구** — 훑고 조작한다 | 콘솔 홈, 편집 패널 | ✅ 현재 유지 (3.0절 1회차) |
| **읽기** — 문장을 읽는다 | 가이드, FAQ | ✅ 현재 유지 (3.0절 2회차) |
| **진입** — 처음 만난다 | 랜딩, 로그인 | ⚠️ 구조적 결함 있음 (3.3절) |

읽는 화면의 줄 길이가 길다는 측정(3.2절)은 **사실이지만 채택 사유가 되지 못했다.** 측정값이
문제를 가리켜도 사용자가 개선으로 느끼지 않으면 고치지 않는다 — 기록만 남긴다.

### 3.2 줄 길이 측정 (한글은 전각이라 줄당 글자수 ≈ 본문폭 ÷ 글자크기)

한글 본문의 읽기 적정선은 **줄당 35~50자**다.

| 화면 | 본문폭 | 크기 | 줄당 글자수 | 판정 |
|---|---|---|---|---|
| 랜딩 리드문 `.l-lead` | 590px | 16px | **37자** | ✅ 적정 |
| 가이드 본문 `.g-section p` | 796px | 12px | **66자** | ❌ 김 |
| 가이드 노트 `.g-note` | 768px | 11.5px | **67자** | ❌ 김 |
| FAQ 답변 `.g-faq-a p` | 732px | 12px | **61자** | ❌ 김 |

랜딩이 "디자인 되어 있다"고 느껴지는 이유가 여기 있다. 같은 팔레트·같은 폰트인데 **리드문만
줄 길이를 37자로 가둬 뒀다.** 가이드·FAQ는 그 장치가 없다.

### 3.3 화면별 구체 결함

**로그인** (`components/login-form.tsx`)
- `<h1>`이 `.c-section-title`을 재사용해 **제목이 13px**이다. 로그인 화면의 제목이 본문보다
  겨우 1.5px 크다
- Google 버튼과 매직링크 버튼이 **둘 다 `.c-btn`**(같은 인디고 채움)이라 위계가 없다
- 인라인 `style={{ flexDirection: "column", textAlign: "left", maxWidth: "none" }}`로 콘솔의
  2단 폼 그리드를 **되돌리고 있다.** 설계된 것이 아니라 덧댄 흔적이다
- 카드 안에 제목·버튼·입력뿐이다. 무엇을 하는 서비스인지, 계정이 없으면 어떻게 되는지가 없다

**랜딩 — 인트로** (`components/landing-home.tsx`)
- 히어로의 제품 미리보기가 **내용 없는 회색 상자**다. `.l-mockup-stats span`(3개),
  `.l-mockup-table div`(4개), `.l-mockup-heading span/strong`이 전부 빈 요소이고 CSS로
  테두리·배경만 칠해져 있다. 제품을 파는 자리의 주 비주얼이 **로딩 스켈레톤처럼 읽힌다**
- 본문 크기가 `10px`(경로 카드 키커) · `11.5px`(경로 설명) · `12px`(흐름 설명) ·
  `13px`(마무리)로 **네 종류**다. 같은 역할의 텍스트가 섹션마다 다른 크기다
- `.l-flow li > span`이 `margin-bottom: 44px` + `min-height: 220px`로 번호를 밀어낸다.
  레이아웃이 아니라 하드코딩된 여백이라 글이 길어지면 어긋난다
- `.l-closing`만 `#111827`·`#f8fafc`·`#94a3b8`를 직접 박아 쓴다 (다른 곳은 전부 토큰)

**사용 가이드** (`app/guide/page.tsx`) — **현재 유지 결정 (3.0절). 아래는 기록용**
- 본문 12px / 노트 11.5px / h2 15px. **h2와 본문의 비가 1.25배**라 섹션 경계가 보이지 않는다
- 결정적으로, **본문 문단 대부분이 `.g-note`**(왼쪽 테두리 + 회색 배경 콜아웃)다. 실제 문서에서
  연속 6개가 이어지는 구간이 있다. **전부가 강조면 아무것도 강조가 아니다** — 페이지가 회색
  박스 더미로 보인다
- 페이지가 긴데 목차가 없어 현재 위치를 알 수 없다

**FAQ** (`app/faq/page.tsx`) — **현재 유지 결정 (3.0절). 아래는 기록용**
- 카테고리 h2 **13px** / 질문 12.5px / 답변 12px. **셋의 차이가 0.5px씩**이라 훑을 수가 없다.
  FAQ는 훑어서 내 질문을 찾는 화면인데 그 기능이 죽어 있다
- 펼침 마커 `＋`가 `--c-faint` — F-01의 대비 미달 토큰이다

### 3.4 F-01은 이 원인의 증상이었다

`--c-faint`가 대비 2.56:1까지 내려간 것은 우연이 아니다. **크기·굵기·여백으로 위계를 만들지
못하니 색을 흐리게 해서 위계를 만들려 한 것**이고, 그 방향은 접근성을 깨는 쪽으로만 갈 수
있다. 2절에서 "토큰 하나의 문제"로 적었지만, 정확히는 **구조적 원인의 국소적 발현**이다.

따라서 F-01을 값만 올려 고치면 그 화면은 위계를 잃는다. **대비를 다른 축(크기·줄길이·여백)에서
확보한 다음** 색을 정상화해야 한다 — 순서가 있다.

> **적용 결과 (T87-10): 이 위험이 실제로 걸린 곳은 4곳 중 1곳(`.g-path dt`)뿐이었다.**
> 나머지는 크기·굵기·서체·위치가 이미 위계를 지고 있었다. 사용처별 판정은 6.3절.

### 3.5 그래서 방향은 "화면 성격에 맞는 밀도"

미니멀리즘은 **이 문제의 해법이 아니다.** 읽는 화면이 밋밋한 것은 장식이 많아서가 아니라
읽기용 타이포가 없어서다. 장식을 더 걷어내도 나아지지 않는다.

| 화면 성격 | 처방 | 대상 |
|---|---|---|
| 도구 | **그대로 둔다** (검증됨 — 3.0절 1회차) | 콘솔 홈, 편집 패널 |
| 읽기 | **그대로 둔다** (검증됨 — 3.0절 2회차) | 가이드, FAQ |
| 진입 | **구조적 결함만 고친다.** 밀도는 건드리지 않는다 | 로그인(완료), 랜딩 |
| 전 화면 공통 | 색·반경·그림자·상태·포커스 일관화 (4절) | 전부 |

> **이 표는 한 번 뒤집혔다.** 초안에는 "읽기 = 본문 15px·줄 45자"가 처방으로 적혀 있었으나
> 3.0절 2회차에서 기각됐다. **가이드·FAQ에 15px를 적용하지 않는다.** 로그인에서 채택된 것은
> 크기가 아니라 구조(13px `<h1>`·버튼 위계·인라인 `style`)였다.

색·반경·그림자를 줄이는 일(M-01~M-05·M-07)은 **여전히 유효하다.** 다만 그것은 일관성 정비이지
"디자인 필"을 만드는 레버가 아니다. 둘을 섞어 논하지 않는다.

## 4. 공통 시각 기준 (제안)

> 5절의 미결 결정이 정해지면 확정한다. 아래는 3.3절의 **"절제된 어휘 + 과감한 대비"**를
> 가정한 안이며, `scratchpad/console-ab.html`의 B안이 이 기준을 실제로 구현한 것이다.

### 4.1 색 — 단일 팔레트

정본은 콘솔의 slate + 인디고 세트다. 이유: 이미 라이트·다크 양쪽이 존재하고,
**T87-10에서 `--c-faint`를 없앤 지금은 전 토큰이 AA를 통과한다** (2절 F-01).
SDK·산출물을 여기에 맞춘다.

- 강조색은 **하나** — `--c-accent` / `--c-btn-bg`
- 상태색은 danger · ok · (필요 시) warn. **개수를 세지 않는다**(AGENTS.md 7절) — 4.6절 표가
  정본이다. 지금 warn 계열은 SDK의
  `#fff4e5`/`#b5560a` 한 곳에만 있고 토큰이 없다
- **가장 흐린 텍스트 토큰은 `--c-muted`다** (라이트 `#64748b` 4.76:1 / 다크 `#94a3b8` 5.71:1).
  이보다 흐린 텍스트 토큰을 새로 만들지 않는다 — `--c-faint`가 그렇게 생겨났고 AA를 깼다.
  더 약하게 보여야 하는 것이 있으면 색이 아니라 **굵기·크기·여백**으로 낮춘다 (4.2절 규칙 2)

### 4.2 타이포 — 전역 스케일을 강제하지 않는다

> **⚠️ 이 절의 초안은 폐기됐다.** 처음에는 `body 14px · title 20px`의 6단계 전역 스케일을
> 처방했으나, 그것이 바로 3.0절 1회차에서 **기각된 콘솔 실험**이다. 같은 처방을 4절에
> 남겨 두면 다음 사람이 기각된 작업을 반복하게 되므로 규칙 자체를 바꾼다.

**각 표면은 현재 크기를 유지한다.** 콘솔 11.5px, 랜딩 14px, SDK 13px, 산출물 81.25%는
그대로 둔다. 화면 성격에 따라 밀도가 다른 것은 결함이 아니다 (3.1절).

규칙은 둘뿐이다:

1. **새 크기를 늘리지 않는다.** 이미 그 표면에 있는 값을 쓴다. 새 값이 필요하면 왜 기존
   값으로 안 되는지를 먼저 적는다 — 공개판의 고정값 16종(1.2절)이 그렇게 늘어났다.
   반응형 `clamp`를 새로 만들 때도 같다
2. **`--c-faint`처럼 대비를 낮춰 위계를 만들지 않는다** (3.2절). 위계가 필요하면 굵기와
   여백으로 만든다

F-04(산출물만 상대값, 나머지는 절대 px)는 **기록만 남긴다.** 전 표면을 `rem`으로 옮기는 것은
본문 크기를 건드리는 일이라 3.0절의 확립된 사실과 충돌한다 — 별건으로 판단한다.

랜딩 삽화(`.l-preview-*`)의 6.5~9px는 **삽화 전용 예외**다. 본문 스케일 논의 대상이 아니다.

### 4.3 간격 — 4px 그리드

`4 · 8 · 12 · 16 · 24 · 32 · 48`. 그 밖의 값은 쓰지 않는다. 현재 1·5·7·9·14·18·22·54px는
전부 이 중 하나로 반올림된다.

### 4.4 반경 — 3단계

| 토큰 | 값 | 용례 |
|---|---|---|
| `--r-sm` | 4px | 배지·코드·작은 컨트롤 |
| `--r-md` | 8px | 버튼·입력·카드 |
| `--r-full` | 999px | 알약·카운트·토글 |

10·12·16px는 `--r-md`로, 3·5·6·7px는 용도에 따라 `--r-sm`/`--r-md`로 접는다.

### 4.5 그림자 — 2단계

| 토큰 | 의미 |
|---|---|
| `--sh-flat` | 면 위에 놓인 것 (카드) — 현재 `--c-shadow` |
| `--sh-raised` | 떠 있는 것 (패널·FAB·모달) |

버튼에는 그림자를 쓰지 않는다. 현재 랜딩의 `.l-primary-action`만 예외적으로
`0 9px 24px rgba(79,70,229,.18)`를 쓴다.

### 4.6 상태 — 전 표면 공통 (개수는 아래 표가 정본)

| 상태 | 규칙 |
|---|---|
| hover | 배경 한 단계 강화. 색상 이동 금지 |
| focus | **`:focus-visible`만.** 2px 링 + 2px offset (F-03). **값은 같되 전달 경로는 표면마다 다르다 — 아래 참조** |
| active | 이동·크기 변화 없음 |
| disabled | `opacity: .5` + `cursor: not-allowed` |
| loading | 텍스트 유지 + 비활성. 스피너 도입은 별건 |
| empty | 중앙 정렬 + `--c-muted`. 다음 행동 링크 1개 |
| error | `--c-danger-*` 3종 세트 (텍스트·배경·테두리) |
| success | `--c-ok-*` 3종 세트 |

색만으로 상태를 구분하지 않는다 — 아이콘이나 문구를 함께 둔다 (WCAG SC 1.4.1).

**포커스 링의 전달 경로.** "전 표면 동일"은 *보이는 결과*를 말하는 것이고, 구현은 표면마다
다를 수밖에 없다. `:root`의 `--c-accent-focus`가 네 표면에 다 닿는다고 가정하면 안 된다:

| 표면 | 경로 |
|---|---|
| 공개판·사내판 | `:root`의 `--c-accent-focus`를 그대로 참조 |
| SDK 패널 | **Shadow DOM 안이라 `:root`가 닿지 않는다.** 4.7절의 `THEME_TOKENS`를 `:host`에 선언해야 한다 |
| 산출물 | `export.ts`가 `THEME_TOKENS`를 **빌드타임에 import**해 링 값을 CSS 문자열에 보간한다. 값이 구워질 뿐 요청은 0건이다 (0절). **손으로 리터럴을 적지 않는다** → 적용은 **#86 이후** |

### 4.7 토큰의 단일 원천

F-02를 없애는 방법이다. 제약을 먼저 적는다:

- `apps/web`은 실제 `.css` 파일을 쓰고 Next가 번들한다
- `packages/server`는 CSS를 **TS 템플릿 문자열**로 내보낸다
- SDK는 **Shadow DOM 안**이라 `:root`가 닿지 않는다 — `:host`에 선언해야 한다
- 산출물은 `export.ts`에서 `@mockspec/shared`를 import할 수 있으므로 **빌드타임 재사용이 가능**하다.
  결과 HTML에 값이 문자열로 구워질 뿐 네트워크 요청은 0건이다 (0절의 정정 참조)
- 빌드 도구 추가 금지 (AGENTS.md 5절 — turbo/nx 금지)

이 제약 아래 가장 단순한 안:

> `packages/shared`에 `THEME_TOKENS`(토큰 → 값 맵)와 그걸 CSS 문자열로 찍는 헬퍼를 둔다.
> `packages/server`·`packages/sdk`는 **직접 import**한다 (셋 다 이미 `@mockspec/shared`
> 의존). `apps/web`은 `globals.css`를 손으로 유지하되, **`globals.css`의 `:root` 블록이
> `THEME_TOKENS`와 일치하는지 검사하는 vitest 1본**을 둔다 — 갈라지면 CI가 잡는다.

`apps/web`도 `@mockspec/shared`에 의존하므로 런타임 주입도 가능하지만, CSS를 JS로 주입하면
FOUC와 SSR 복잡도를 사는 대신 얻는 것이 없다. **파일은 그대로 두고 테스트로 묶는 쪽**이
"단순하고 범용적"에 맞는다.

### 6.3 F-01 적용 상세 (T87-10, 2026-08-02)

Q-04 결정에 따라 **`--c-faint` 토큰을 삭제**하고 사용처를 `--c-muted`로 옮겼다.
`globals.css`와 `shell.ts`를 **같은 커밋에서** 고쳤다 — F-02 때문에 한쪽만 고치면 갈라진다.

| 위치 | 전 | 후 |
|---|---|---|
| `globals.css` `:root` / `:root[data-theme="dark"]` | `--c-faint` 선언 | **삭제** |
| `shell.ts` 같은 두 블록 | `--c-faint` 선언 | **삭제** |
| `.c-project-meta` (`globals.css`·`console.ts`) | `--c-faint` | `--c-muted` |
| `.c-extension-steps li::before` (`globals.css`) | `--c-faint` | `--c-muted` |
| `.g-faq-item summary::before` (`globals.css`·`pages.ts`) | `--c-faint` | `--c-muted` |
| `.g-path dt` (`pages.ts`) | `--c-faint` | `--c-muted` + **`font-weight: 500`** |

**3.4절이 요구한 "다른 축에서의 대비"는 한 곳에만 필요했다.** 나머지 세 곳은 색을 올려도
위계가 유지되기 때문이다 — 크기·굵기·서체·위치가 이미 구별을 만들고 있다:

| 사용처 | 색 외의 구별 수단 | 조치 |
|---|---|---|
| `.c-project-meta` | 형제 `.c-project-name`이 12.5px·600·`--c-text`. 크기 1.5px + 굵기 200 차 | 없음 |
| `.c-extension-steps li::before` | 10px·700·모노스페이스·`position: absolute`로 본문 밖 | 없음 |
| `.g-faq-item summary::before` | 장식 마커. 나란한 질문 텍스트가 12.5px·600·`--c-text` | 없음 — 펼침/접힘은 **상태 정보**라 대비 상승이 순이익 |
| `.g-path dt` | **없었다.** 짝인 `dd`가 `--c-text-3`(`#475569`)라, `dt`를 `--c-muted`(`#64748b`)로 올리면 용어와 설명의 색차가 좁아진다 | **`font-weight: 500`** — 4.2절 규칙 2대로 굵기로 위계를 만든다 |

크기·여백은 건드리지 않았다. **3.0절의 확립된 사실(본문 크기를 키우지 않는다)과
"새 크기 값을 만들지 않는다"(4.2절 규칙 1)에 걸리기 때문**이고, 위 표대로 그럴 필요도 없었다.
`font-weight: 500`은 `pages.ts`에 이미 여러 번 있는 값이라 새 값이 아니다.

**대비 계산값** (7절 요구 — 2절과 같은 형식). 배경은 실제로 이 텍스트가 놓이는 세 가지를
전부 잰다. `.c-project:hover`가 `--c-surface-2`로 바뀌므로 **호버 상태도 따로 확인해야 한다**:

## 7. 검증 방법

각 단계에서 다음을 기록한다 (완료 조건 마지막 항목).

- `npm run typecheck` · `npx vitest run` · 해당 E2E
- 대비: 변경한 색 조합의 계산값을 이 문서 2절 형식으로 표에 남긴다
- 뷰포트 390 · 768 · 1280 · 2400px에서 가로 오버플로 0건
- 라이트·다크 각각에서 키보드 Tab 순회 — 모든 포커스 가능 요소에 링이 보일 것

### 7.1 시각 검증은 렌더한 이미지로 한다

인터랙티브 비교 페이지는 쓰지 않는다 (3.0절 4회차). **Playwright로 실제 앱을 띄워
렌더한 정지 이미지**를 비교한다. Playwright는 이미 devDependency다.

**손으로 적은 마크업으로 비교하지 않는다.** 화면은 TSX 컴포넌트가 만들고, 마크업을 복사해
두면 컴포넌트가 바뀔 때 조용히 낡는다 — "현재 화면"이 실제와 달라지면 비교가 무의미해진다.
실제 라우트를 띄워 찍는다.

**기준(before)은 반드시 별도 리비전에서 빌드한다.** 같은 작업 트리에서 커밋 전후를 비교하면
커밋한 뒤에는 둘이 같아져 "차이 없음"으로 잘못 나온다. 임시 워크트리를 쓴다:

```bash
# 1) 기준 리비전을 임시 워크트리에 펼쳐 빌드한다 (base는 보통 origin/main)
git worktree add ../ui-base origin/main
cd ../ui-base && npm ci && npm run build && npm run build -w @mockspec/web
npx next start apps/web -p 4401 & BASE_PID=$!

# 2) 현재 브랜치도 같은 방식으로 띄운다
cd - && npm run build && npm run build -w @mockspec/web
npx next start apps/web -p 4402 & HEAD_PID=$!

# 서버를 반드시 거둔다 — 안 그러면 다음 비교가 4401/4402에서 EADDRINUSE로 죽고,
# 지워진 워크트리를 붙든 프로세스가 남는다
trap 'kill $BASE_PID $HEAD_PID 2>/dev/null; wait $BASE_PID $HEAD_PID 2>/dev/null' EXIT

# 3) 두 포트를 같은 스크립트로 찍어 비교한다 (아래)

# 4) 끝나면 서버를 내리고 워크트리를 지운다 — AGENTS.md 6절 "병합 후 정리"
kill $BASE_PID $HEAD_PID; wait $BASE_PID $HEAD_PID 2>/dev/null
git worktree remove ../ui-base
```

찍는 쪽은 라우트와 포트만 받으면 된다:

```js
import { chromium } from "playwright";

const ROUTES = ["/", "/login"];
const PORTS = { before: 4401, after: 4402 };
const browser = await chromium.launch();

for (const route of ROUTES) {
  for (const [tag, port] of Object.entries(PORTS)) {
    for (const width of [390, 1440]) {
      for (const theme of ["light", "dark"]) {
        const page = await browser.newPage({ viewport: { width, height: 1000 }, deviceScaleFactor: 2 });
        await page.goto(`http://localhost:${port}${route}`, { waitUntil: "networkidle" });
        await page.evaluate((t) => document.documentElement.setAttribute("data-theme", t), theme);
        // 가로 오버플로는 눈으로 보지 말고 계산한다 — 0이 아니면 실패
        const overflow = await page.evaluate(
          () => document.documentElement.scrollWidth - document.documentElement.clientWidth,
        );
        console.log(route, tag, width, theme, "overflow:", overflow);
        await page.screenshot({ path: `${route.replace(/\W/g, "_")}-${tag}-${width}-${theme}.png`, fullPage: true });
        await page.close();
      }
    }
  }
}
await browser.close();
```

**계산으로 잡히지 않는 회귀도 있다.** `text-align` 상속이 그 예다 — 히어로를 가운데 정렬하면서
미리보기 안의 어노테이션 설명까지 끌려갔는데(PR #89 리뷰), 오버플로는 0이라 통과했다.
레이아웃 속성을 부모에 걸었을 때는 **상속되는 속성인지 확인하고 자식의 계산값을 찍어 본다:**

```js
await page.evaluate(() => getComputedStyle(document.querySelector(".l-note p")).textAlign);
```
